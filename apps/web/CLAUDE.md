@AGENTS.md

## Web app (`web`)

Next.js 16 App Router app. Repo-wide commands and layout are in the root `CLAUDE.md`.

### Commands (run in `apps/web`, or prefix with `pnpm --filter web`)

```bash
pnpm dev           # next dev on http://localhost:3000
pnpm build
pnpm lint          # eslint-config-next (core-web-vitals + typescript)
pnpm check-types   # next typegen && tsc --noEmit
```

### Notes

- Source lives in `src/`; alias `@/*` → `src/*`. Routes in `src/app/`.
- `next.config.ts` enables `cacheComponents` and `partialPrefetching` — check the bundled docs in `node_modules/next/dist/docs/` for how these change data fetching/caching before writing server code.
- Route prop types (`LayoutProps<"/">`, `PageProps`) are global helpers generated by `next typegen`; run `check-types` (or `dev`) after adding routes so they exist.
- Tailwind v4, CSS-first: no `tailwind.config`; theme tokens are CSS variables in `src/app/globals.css` (`@theme inline`). Dark mode is class-based (`.dark` ancestor).
- shadcn/ui uses the `base-nova` style built on `@base-ui/react`, not Radix — component APIs differ from Radix-based shadcn. Add components with `pnpm dlx shadcn@latest add <name>`; they land in `src/components/ui/`.
- `cn` comes from the `cn` npm package (re-exported from `src/lib/utils.ts`), not `clsx` + `tailwind-merge`.
- Icons: `lucide-react`.
- Screens read data only through `src/data/<area>.ts` (one async function per screen). Until a procedure exists these return typed fixtures from `src/mocks/` (keyed by organization code; only the exception demo rows and `tenants.ts` remain; Accounts, Tariffs, Work Orders and GIS are real). Settings and licensed modules are real (`getSession().organization`); module data functions call `requireModule(module, permission?)`. Swap the function body for the tRPC call in the PR that ships the procedure. See `docs/build-plan.md` → "UI track".
- Request-time reads go inside `<Suspense>`. Anything that reads the clock calls `await connection()` first; `cookies()` alone does not make a subtree request-time under partial prefetching.
- `/design` previews the tokens. Grids use `DataGrid` (`src/components/data-grid.tsx`, TanStack Table v9); money uses `MoneyText` and never converts to `number`.
- Auth: Better Auth at `/api/auth/[...all]`, created lazily in `src/server/auth.ts`. `src/data/session.ts` reads the session and the user's one organization, and redirects to `/sign-in` without them. Sign-in sends the organization code header with email or a qualified username; sign-out uses `authClient` from `src/lib/auth-client.ts`. There is no organization switching (requirements §1). `getSession()` also returns `access` (role and permissions); `getApi()` gives an in-process tRPC caller acting as the user. Data functions call `requirePermission(p)` (not found without it) and nav items carry a `permission`; hiding is wayfinding only, procedures enforce. `/settings/team` grants and revokes extra permissions via a server action (`refresh()` after). Permission and role labels are in `src/lib/permission-labels.ts`. `/settings/areas` shows and edits the hierarchy and routes (`src/data/hierarchy.ts`); the team sheet's Coverage section sets scope restrictions. `access.scope` limits what the procedures return (the Accounts procedures filter by area and route ids themselves). `authClient` and the in-process caller name themselves as `web` for the audit log. The exception queue (`src/data/exceptions.ts`) shows real kernel exceptions with take, assign, retry and resolve actions (`/exceptions` server actions), plus demo rows from `src/mocks/exceptions.ts` (marked `demo`, no actions) for module queues that have not shipped. `/settings/audit` (needs `audit:read`) lists entries with filters, paging and the chain check; action names are in `src/lib/audit-labels.ts`. `/settings/organization` edits time zone and language (`src/data/config.ts`, a new configuration version per save, with its history) for members with `settings:manage`, and shows them read-only otherwise; language labels are in `src/lib/languages.ts`. Never import a non-component value from a `"use client"` file into a server component: it arrives as a client reference. `/settings/support` (needs `access:manage`, `src/data/support.ts`) grants, lists and revokes Flowless support access. The header bell (`src/components/shell/notification-bell.tsx`, `src/data/notifications.ts`) shows in-app notifications, polls once a minute, and marks them read when opened. `src/lib/tree.ts` flattens parent-linked lists for display.

### Work Orders and GIS screens (Phase 2 W4)

- Data: `src/data/work-orders.ts` (`listJobs`, `getNewJobForm`, `getJob`, `listReviews`, `listCrews`; every one gates on `requireWork`: Work Orders or GIS licensed and some work-order permission, else not found) and `src/data/gis.ts` (`getNetworkMap({ branch, jobId, dmaId })`, `listPendingBranches`, `getBranchPreview`, both of the last needing `gis:post`). `src/data/people.ts` turns user ids into names (member list, falling back to the caller). Mutations are server actions: `app/(staff)/work-orders/actions.ts`, `app/(staff)/map/actions.ts`, `map/reconcile/actions.ts`, all through `runAction` (`src/data/run-action.ts`: error message or data, then `refresh()`). Device-style actions mint their `eventId` in the browser; a refused or stale outcome comes back as data and `settled()` turns it into the dialog's error. No tRPC HTTP client is used.
- Routes: `/work-orders`, `/work-orders/new`, `/work-orders/[id]`, `/work-orders/reviews`, `/work-orders/crews`, `/map` (`?branch=`, `?job=`, `?dma=`), `/map/reconcile`, `/map/reconcile/[branch]`. Nav items use `anyModule` and `anyPermission` (`components/shell/nav.ts`); `currentHref` picks the most specific item.
- Map (`app/(staff)/map/`): `network-map.tsx` holds the state (tool, selection, trace, drafts) and decides what each click does; `use-network-map.ts` owns the MapLibre instance (sources, layers, filters, paint) and reports clicks with what was under them; `geojson.ts` is pure builders (tested); `map-config.ts` has styles and colours (hex, as MapLibre cannot read CSS variables; dark mode dims the raster paint instead of loading another style); panels are `layers-panel`, `trace-panel`, `dma-panel`, `asset-panel`; create dialogs in `create-dialogs.tsx`. The map is client-only (`map-loader.tsx`, `next/dynamic` with `ssr: false`) and remounts per branch. maplibre-gl is pinned to 6.12.0; `next.config.ts` copies its worker to `public/maplibre/` (gitignored, ignored by eslint) and the map sets that URL, because bundling the worker is unreliable under Turbopack (Majimap hit it too). The container must not be `absolute`: MapLibre's CSS sets `position: relative` on it.
- Edits always name a branch. The live network needs `gis:post`; the UI hides edit tools otherwise and says why, and the procedures enforce it. Recording a condition or valve log on a job's branch links it to the job (`workOrders.linkLog`).
- Tests: `pnpm --filter web test` (Vitest, no database): nav gating and GeoJSON builders.

### Accounts screens (Phase 3 F5a)

- Data (all gate on `requireAccounts` = Accounts licensed and `accounts:read`, else not found; the API enforces scope): `src/data/accounts.ts` (`listAccounts({ q, commercialStatus, serviceStatus, areaId, routeId, after })` keyset-paged 50 a page, or `accounts.search` when `q` is set; `getAccountPage(number)` reads the account, customer and contacts, commands, holders, activation status, relocations, membership classes and write-off approvals through their own procedures; `getCategories` reads Tariffs' categories only when Tariffs is licensed and `tariffs:read` is held, else there is no category column; `getPlaceNames`; `findAccounts` for the palette), `src/data/customers.ts` (`listCustomers`, `getCustomerPage`, `getAccountFormOptions`), `src/data/applications.ts` (`listApplications`, `getApplicationPage`, `getSurveyJobPrefill`) and `src/data/approvals.ts` (`listApprovals`). Never put functions in what a data function returns to a client component (the account page object is passed whole): `pointPlaces` holds the place labels as plain data.
- Routes: `/accounts` (`?q`, `status`, `service`, `area`, `route`, `after`), `/accounts/[number]`, `/accounts/new`, `/accounts/customers`, `/accounts/customers/[id]`, `/accounts/applications` (`?stage`), `/accounts/applications/new`, `/accounts/applications/[id]`, `/approvals` (`?view=to_decide|open|closed`). List state lives in the URL (`components/list-filters.tsx`: `ListFilters`, `NextPage`); lists are server-rendered tables, not `DataGrid`, because search, filters and paging are the API's. The nav lists Approvals (any member) and the Accounts group (Accounts, Customers, Applications; module `accounts` and `accounts:read`) flat, in that order; the command palette searches accounts live through `searchAccountsAction` instead of preloading them.
- Actions: `app/(staff)/accounts/actions.ts` (customers, contacts, account and service point creation, `runLifecycle` for every status command, gate tick/untick, write-off request, succession, change of name, relocation steps, and the search/preview helpers), `accounts/applications/actions.ts` (create, survey, advance, convert, reject/cancel) and `approvals/actions.ts`, all through `runAction`. Every command dialog (`ActionDialog`) mints its `id` with `crypto.randomUUID()` on each opening, so a retried submit replays; a refusal is the dialog's error. `runAction` turns validation-issue JSON into its messages (`lib/error-message.ts`).
- Account page: lifecycle buttons come from `lib/account-lifecycle.ts` (wayfinding that mirrors the state machine; the procedure decides), the activation panel shows each gate with its decider, tick/untick with a note, and Activate (the override box appears only with `settings:manage`); terminate shows the "no ledger" acknowledgement plainly and can cite an approved write-off; request write-off asks for approval (amount typed as money, parsed to minor units in the action); change of name cannot be dated before the day after the current holder took over; relocations (request from the button row, then survey, work, complete, cancel in `relocations-panel.tsx`). The statement section is a placeholder that says the ledger arrives with Billing (Phase 4): the old mock ledger belonged to mock accounts that are gone, and showing it on real accounts would show another person's invoices. `src/mocks/accounts.ts` was deleted.
- Forms: `components/accounts/customer-chooser.tsx` (existing customer search or a new customer with contacts, with the duplicate warning from `customers.duplicates`) and `place-fields.tsx` (address, scheme > zone > DMA pickers that offer only what sits under the one above, route, latitude/longitude and "use my position"); the pure mappers are `lib/account-forms.ts`, `lib/area-options.ts`, `lib/application-view.ts` (stage line with waived stages as skipped; the next action). `/accounts/new` saves in steps (customer, account, service point) and remembers what worked, so a retry does not repeat it.
- Applications: the stage line, the survey (record result, approval pending/decided and its decisions), the next advance action (invoice and payment take a reference), convert (opens the account and goes to it), reject/cancel. "Raise survey job" links to `/work-orders/new?kind=connection_survey&asset=<application id>` (prefilled title, position and note) and shows only at Work Orders level full. Survey and write-off approvals are decided on `/approvals` (small: three views, approve with an optional note, reject with a reason, withdraw).
- Known gaps: no map picker for coordinates; categories cannot be changed on an existing account (no procedure); membership class cannot be edited after opening; the account list has no category filter (the API has none); a search returns its best 100 without paging; the place pickers offer every area even to a scope-limited member (the API refuses what is outside their scope); successors take the same category; relocation has no fee-code picker.
- Tests: `lib/accounts-helpers.test.ts` (stage line, offers, lifecycle actions, form mappers, area pickers, error messages) and `nav.test.ts` (Accounts group, Approvals).

### Tariffs and data-quality screens (Phase 3 F5b)

- Data: `src/data/tariffs.ts` (all gate on `requireTariffs` = Tariffs licensed and `tariffs:read`, else not found; a malformed id is not found too: `listTariffs`, `getTariffPage(id)`, `getNewTariffForm`, `getCategoriesPage`, `getChargeCatalog`, `listInvoiceTypes`, `getInvoiceTypePage(id)`; making a change needs `tariffs:manage`, the UI hides buttons otherwise and the procedures enforce), `src/data/account-settings.ts` (`getAccountsSettings`: `requireModule("accounts", "settings:manage")`, the eight settings through `config.list` and `config.history`, the charge items for the membership picker only when Tariffs is readable) and `src/data/data-quality.ts` (`getDataQualityPage(rule)`: summary, rules, duplicate groups and the chosen rule's first findings page; `accounts:read`). Bigint money passes through the in-process caller and into client components as `bigint`; typed amounts always travel as text and become minor units in the server action (`lib/money-input.ts`, currency-aware), never as `number`.
- Routes: `/tariffs`, `/tariffs/new`, `/tariffs/[id]`, `/tariffs/categories`, `/tariffs/charges`, `/tariffs/invoice-types`, `/tariffs/invoice-types/[id]`, `/settings/accounts`, `/accounts/data-quality` (`?rule=`). Nav: Tariffs group (Tariffs, Categories, Charge catalog, Invoice types; module `tariffs` and `tariffs:read`), Data quality with the Accounts group (`accounts:read`), Accounts settings under Settings (module `accounts` and `settings:manage`).
- Actions: `app/(staff)/tariffs/actions.ts` (every tariffs change through `runAction`; typed content arrives as a draft and is parsed with the same `parseDraft` the form uses, then the API validates again), `app/(staff)/settings/accounts/actions.ts` (`saveAccountSettingAction`: whitelists the eight keys, turns an optional date into midnight in the organization's time zone, `config.set` with `expectedVersion`) and `accounts/data-quality/actions.ts` (load more for findings and duplicates, no refresh).
- Tariff versions: `lib/tariff-view.ts` (`versionStatus`: in force, scheduled, superseded or replaced before it started; `versionTimeline`; `contentTable`; the category assignment helpers where "keep" is left out, "none" is `null` and the outcome lines say what carries over from the assignment in force on the effective date), `lib/effective-date.ts` (`previewEffectiveDate`: the "takes effect on" line and the closed-period and arrived-version refusals) and `lib/tariff-content.ts` (band, uniform and flat drafts; each band only asks for where it ends, so bands meet by construction). The API's pure rules (`validateTariffContent`, `planEffectiveDate`) are server code the browser cannot import, so the checks are mirrored in `lib`, with the API as the authority and `tariffs-helpers.test.ts` comparing both on the same inputs. Components: `components/tariffs/` (`ContentTable`, `ContentEditor` with a "try a reading" price check, `EffectiveDateField`).
- Invoice types: `lib/invoice-type-form.ts` maps the stored type, line template and late-fee rule to text fields and back (percentages as basis points, amounts as minor units); `allowedOverdueActions` mirrors T-09 so an application's invoice is never offered `disconnect`. The simulate panel calls `tariffs.simulateLateFee` through `simulateLateFeeAction` (debounced, nothing is written).
- Accounts settings: `lib/account-settings.ts` has each setting's defaults-to-form and form-to-value mapper (`numberingToForm`, `statusRulesFromForm`, `activationFromForm`, `applicationFromForm`, `membershipFromForm`, `dataQualityFromForm`, `approvalPolicyFromForm`), `effectiveFromOf` and `summarize` for the history; `lib/account-number.ts` mirrors the numbering preview. Each form is wrapped in `settings/accounts/setting-shell.tsx`: the version in force and scheduled ones, fields, optional date and reason, Save as a new version checked against the newest version the form saw (a conflict says someone else changed it and offers Reload), and the history. The form remounts per `latestVersion`. `approvals.accounts.connection_survey` and `approvals.accounts.write_off` are edited here with a small policy editor (levels with a permission picker and optional minimum amount, escalation hours and permission); there is no generic approvals-policy page yet.
- Data quality: `lib/data-quality-view.ts` (`ruleTiles`: count toned by severity, "Waiting on Metering" for a rule with no source, "disabled"; `cleanHeadline`; `defaultRule`). Rows link to the account and customer pages; a rule that raises exceptions links to `/exceptions?type=DATA_QUALITY`.
- Known gaps: not driven in a browser; invoice types cannot be created from the UI; a charge item's inventory link is not editable; no tariff-level history of who changed what beyond the version notes (the audit log has it); the dev seed leaves Tariffs' default categories, charges and invoice types to the `entitlements.changed` consumer, which only runs when the outbox is drained (run `pnpm db:seed` twice or start the worker).
- Tests: `lib/tariffs-helpers.test.ts` (money parsing, content drafts, mirror parity with the API's rules, effective-date preview, version timeline, assignment carry-over, invoice type forms), `lib/account-settings.test.ts` (every form mapper round-trips and is accepted by the setting's own schema; scheduled dates; the numbering mirror), `lib/data-quality-view.test.ts` and `nav.test.ts` (Tariffs group, Data quality, Accounts settings).
