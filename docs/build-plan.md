# Flowless: Build Plan

This plan says **when** each requirement is built and **where in the code** it lives. **What** each ID means is in [requirements.md](requirements.md); that file is the source of truth for behaviour.

A phase is done only when its **Done when** checks pass. CI runs lint and type checks; tests are off in CI for now and run locally (`pnpm test`) until it is restored. Do not start the next phase on red tests.

## Code layout

Flowless is a modular monolith in one pnpm + Turborepo repo. Every module is a folder with a hard boundary, not a separate service (NF-30).

```
apps/
  web/              Next.js: staff UI and portal. Hosts the tRPC HTTP handler at
                    src/app/api/trpc/[trpc]/route.ts and Better Auth at /api/auth/[...all]
                    (Phase 1). Server code calls procedures in-process.
  mobile/           Expo: technician app (U-02). tRPC client only; imports `type AppRouter`.
  worker/           Node process (added in Phase 1): outbox dispatcher, event consumers and
                    queued jobs (billing runs, imports, reconciliation, messaging) (NF-12).
packages/
  api/              tRPC. The only place procedures live.
    src/
      trpc.ts       initTRPC, context (session, organization_id, scopes, entitlements),
                    base procedures: publicProcedure, tenantProcedure, moduleProcedure(module)
      root.ts       appRouter: one key per module router; `export type AppRouter`
      wiring.ts     the composition root: calls each module's `register(work)` and
                    `registerKernel(kernel)`. The kernel imports no module; a new module
                    adds its lines here and nowhere in the kernel.
      kernel/       tenancy, rbac, entitlements, workflow, audit, outbox, config, files,
                    notifications, exceptions. Always on.
      modules/
        <module>/
          router.ts   tRPC procedures: input validation, then a call into service.ts
          service.ts  use cases; the only code that touches this module's tables
          events.ts   events this module publishes and the consumers it registers
          index.ts    the module's published interface: what other modules may import, plus
                      `register(work)` (Work Registry adapters) and `registerKernel(kernel)`
                      (consumers, settings, approval kinds, reports, file subjects, jobs)
  network/          Pure graph traces over the water network (Phase 2): directional, isolation,
                    subnetwork and DMA membership. Shared by the API, web and mobile. No I/O.
  billing-engine/   Pure library (Phase 4): pricing, scaling, estimate, true-up, validators,
                    rollover, void, correct, final bill. No I/O, no DB, no clock.
  db/               Drizzle: client, one schema file per module (each in its own Postgres
                    schema), migrations, RLS policies, withTenant(organizationId, fn).
                    src/schema/auth.ts is generated by Better Auth and exported only as
                    @flowless/db/auth-schema.
  auth/             Better Auth (organization + twoFactor plugins): users, sessions,
                    organizations, members, invitations, MFA, sign-in rate limits (NF-05).
                    Owns the `auth` Postgres schema. Used by the api context to resolve the
                    session; holds no tRPC procedures.
  shared-types/     Platform-neutral types used by web and mobile (IDs, Money, enums).
  eslint-config/, typescript-config/   shared tooling.
```

### Identity and tenancy

Better Auth is the identity layer, and its `organization` table is the tenant table: every `organization_id` in a module schema references `auth.organization.id` (UUIDs).

| Concern | Owner |
| --- | --- |
| Users, sessions, passwords, MFA, sign-in rate limits (NF-05) | Better Auth core and `twoFactor` |
| Organizations, members, invitations, member roles, the session's active organization (K-01, K-03) | Better Auth `organization` plugin. One membership per user (unique index on `auth.member.user_id`); the active organization is set from it when the session is created and cannot be switched. |
| Sign-in by organization code: email for owners and admins, `<code>.<username>` for other staff (requirements §1) | `packages/auth` sign-in hook and Better Auth `username` plugin |
| Role permissions, such as "can approve a rebate" (K-03) | Default roles, each a list of `<resource>:<action>` permissions (`@flowless/shared-types` permissions), registered with Better Auth access control so it accepts the role names. A member's permissions are their role's defaults plus extra permissions an administrator granted them (`kernel.member_permission`, RLS, deleted with the membership). Checked in `packages/api` (`permittedProcedure`); granting needs `access:manage`, and only permissions the granter holds. |
| Per-scope restrictions by scheme, zone or route (K-03) | Kernel tables. Better Auth roles do not restrict data. |
| Module licensing (K-04), hierarchy (K-02), audit (K-06), support access (K-12) | Kernel. Better Auth hooks feed audit records and publish organization lifecycle events. |

Request flow: `createContext` resolves the caller from the request headers (`connectAuth().getCaller`: the Better Auth session plus the current membership, read fresh). `tenantProcedure` rejects a session without an active organization or whose membership is gone or elsewhere, opens `withTenant` with it, and loads the member's permissions. RLS still decides what each query sees.

Module folder names (one per entry in requirements §3): `accounts` (customers, accounts, service points), `tariffs`, `metering`, `billing`, `payments`, `communications`, `collections`, `work-orders`, `inventory`, `gis`, `nrw`, `portal`, `reporting`, `migration`, and later `finance`.

### Boundary rules

These rules turn the CLAUDE.md rules into code. Each one is enforced by a check, not by review alone.

| Rule | Enforced by |
| --- | --- |
| The auth role's only access outside `auth` is `INSERT` on `kernel.audit_log` and `kernel.outbox_event` (policies `auth_insert`), so identity events are audited (K-06) and organization lifecycle events published (K-09); it can read nothing there. | grants in `0009_kernel_audit_append_only.sql` and `0011_kernel_outbox_claim.sql`; audit and lifecycle tests |
| The worker finds due events and jobs across tenants only through `kernel.claim_outbox()` and `kernel.claim_jobs()`, which return routing fields; each consumer or job then runs inside `withTenant` for its organization (K-09, NF-12). | SECURITY DEFINER functions granted to `flowless_app` only; outbox and job tests |
| The `auth` schema is the one exception to tenant RLS: Better Auth must work before any tenant is known (sign-in, invitations). It is isolated by role instead: `flowless_auth` reaches only `auth`, `flowless_app` never does, and only `packages/auth` imports `@flowless/db/auth-schema`. Modules learn about organizations through events, never by reading `auth.*`. | per-schema grants in migrations; role-separation tests; `flowless/module-boundaries` outside `packages/auth` |
| Every request runs inside `withTenant`. That sets `app.organization_id` for the transaction, and RLS does the rest (K-01, NF-01). No procedure or job gets the raw connection. | `tenantProcedure`, the app DB role without `BYPASSRLS`, isolation canary `packages/api/src/isolation-canary.test.ts` (NF-02): tenant B seeded in every tenant table, every procedure called as tenant A (also aimed at B's ids) returns no B identifier and changes no B row; every procedure must have an entry in its call list, and every registered report is run too |
| Every module procedure checks the module's entitlement on the server (K-04, NF-03). | `moduleProcedure(module)` is the only builder module routers may use; `flowless/module-boundaries` rejects the other builders in module folders |
| A module imports only its own `@flowless/db` schema file. To reach another module it uses that module's `index.ts` or an event (NF-30). | ESLint rule `flowless/module-boundaries` (`packages/eslint-config/boundaries.js`): cross-module imports only through `index.ts`, the kernel likewise, own `@flowless/db/schema/<module>` only; per-module Postgres schemas with grants |
| A module that is not licensed has no router mounted for that tenant and no consumers running for it (NF-31). | `packages/api/src/module-matrix.test.ts` over `moduleMatrix()` (shared-types: none, all, each module absent with its dependents, each module alone with its requirements): every procedure answers without an internal error, an unlicensed module's procedures answer NOT_FOUND, and the worker's dispatch, jobs and escalation run. Module routers mount at the camelCase of their module key; a new kernel router is added to the test's kernel list. |
| Money is `bigint` minor units plus currency (B-18). It crosses the wire through a tRPC transformer that supports `bigint`. | `Money` type in `shared-types`; no `number` money fields in schemas |
| Ledger, readings and invoices are insert-only (NF-22). | DB grants (no `UPDATE`/`DELETE` on those tables for the app role), tests |
| Heavy work is enqueued from a procedure and run by `apps/worker` (NF-12). Every failure becomes a row in the exception queue with owner and age (NF-24). | kernel job runner wraps every job; no bare `try/catch` that swallows |
| `apps/mobile` never imports runtime code from `@flowless/api`; it imports types only. | `flowless/module-boundaries`, applied by `apps/mobile`'s `expo lint` (done in W5) |

**How the work is run (the owner's standing process)**

- Never `git push`. Work on local branches and fast-forward them into local `main`.
- Propose a task list first (steps like F1 to F6), then one agent per step in its own git worktree; the agent commits small and reports; the lead rebases, merges fast-forward only, deletes the worktree and branch, and re-runs lint, types and the whole test suite on `main` before calling the step done. Agents never merge into `main`, never push, and use a scratch database (dropped afterwards) rather than the shared dev database.
- Agents sometimes die on network errors mid-step. They commit as they go, so resume the same agent (SendMessage) after checking its worktree; do not restart from scratch.
- Tests are off in CI until Phase 6; run them locally. A step is done only when its acceptance checks pass on `main`.

## Phases

Each phase lists the requirement IDs it owns. An ID is owned by exactly one phase; a later phase that extends it says so.

### Phase 0: Foundations

**Deliverables:**

### Phase 1: Kernel

**Scope:** K-01 to K-10, K-12, X-02, X-04 (K-11 moved to Phase 6). NFRs: NF-01, NF-02, NF-03, NF-07, NF-24, NF-30, NF-31, NF-32.

**Code:** `packages/api/src/kernel/*`, `packages/auth`, `packages/db` (kernel schema), `apps/worker` (new).

**Deliverables:**

- Better Auth wired up: secret and base URL from env, handler at `/api/auth/[...all]` in web, `@better-auth/expo` for mobile, access-control statements, audit hooks (K-06), organization lifecycle events.
- `createContext` resolves the Better Auth session; `tenantProcedure` uses its `activeOrganizationId` and rejects sessions without one.
- Default roles with permission arrays plus per-member extra permissions (K-03, done in A2). Scope restrictions (K-03, done in A3): a member limited to areas and routes covers everything below them; no restriction rows means the whole organization; modules filter with `ctx.scope()` and `scopeCovers`. Support access (K-12, done in A10): an administrator (`access:manage`) grants a named Flowless engineer read-only access for a reason and at most 72 hours (`kernel.support_grant`, never deleted, revocable). The engineer is never a member; Flowless's own tooling calls the API with `supportSession(...)`, `tenantProcedure` checks the grant on every call, refuses mutations, and audits every call (`support.read`, `support.refused`, source `support`). Browser sessions can never carry a support grant.
- `tenantProcedure` and `moduleProcedure` builders as the entitlement guard for routes and reports (K-04, done in A4): licences are rows in `kernel.organization_module`, set only server-side by Flowless (`setEntitlements`, which rejects modules whose hard dependencies in `MODULE_REQUIRES` are missing); an unlicensed module answers NOT_FOUND before permissions are checked.
- Generic approval engine (K-05, done in A9): `kernel.approval_request` and the append-only `kernel.approval_decision`. A module defines a kind with `defineApproval({ key, module, reasonCodes, policy })`, registers it with `kernel.approval(...)` from its `registerKernel` (`kernel/approval-registry.ts` holds the list, `src/wiring.ts` calls the module), and asks with `ctx.requestApproval(kind, …)` in its own procedure. The policy (levels, each a permission with an optional minimum amount; SLA hours; escalation permission; reason codes) is a configuration-store setting `approvals.<kind>`, so organizations change it without code, and a request keeps the snapshot it was made under. Nobody decides their own request or two levels of one; rejecting needs a note. Outcomes go out as `approval.decided`, applied by the module's `defineApprovalConsumer`. The worker escalates requests past their SLA (`kernel.overdue_approvals()`) into the exception queue as APPROVAL_OVERDUE, after which the escalation permission may decide. The approvals inbox on web ships with the first module that requests approvals.
- Audit log (K-06, NF-07, done in A5): `kernel.audit_log`, insert-only for the app role and the auth role, hash-chained per organization by a trigger and checked by `kernel.verify_audit_chain()`. Procedures write `ctx.audit(...)` in the same transaction as the change; Better Auth hooks record sign-ins (including refused ones), member, invitation and account changes. Each entry has actor, source (web, mobile, api, import, system), before and after.
- Outbox, with a dispatcher in `apps/worker` (K-09, done in A6): `ctx.publish(event, payload)` writes `kernel.outbox_event` in the change's transaction; the worker claims due events through `kernel.claim_outbox()` and delivers them to consumers that modules add with `kernel.consumer(...)` from `registerKernel` (list in `packages/api/src/kernel/consumers.ts`, wired in `src/wiring.ts`).
- Idempotent event consumer helper, with a `replay` flag (done in A6): one receipt per consumer and event (`kernel.consumer_receipt`), per-consumer retry with backoff, `failed` after the last attempt, consumers of unlicensed modules skipped; `replayEvents` re-delivers with `replay: true`. Onboarding publishes `organization.created` (initial settings from organization metadata), whose kernel consumer creates the settings row.
- Configuration store (K-10, NF-32, done in A8): `kernel.config_version`, append-only, one row per version of a setting. A module defines its settings in code with `defineSetting({ key, module, schema, default })` and registers them with `kernel.setting(...)` from its `registerKernel` (list in `packages/api/src/kernel/config-registry.ts`); procedures read the value in force with `ctx.config(setting)`, and jobs read the value at a past date with `readSetting(tx, setting, at)`. `config.set` (needs `settings:manage`) appends a version, from now or a future date, never a past one. It refuses an editor working from an old version (CONFLICT), and audits before and after. Settings of unlicensed modules are hidden. Time zone and language are the first setting (`kernel.regional`); currency stays fixed in `organization_settings`.
- Exception queue (X-02 framework) fed by the job runner (NF-24), done in A7: `kernel.exception` (one open row per dedupe key, owner falls back to unassigned when they leave, area and route for scope) and `kernel.job` (`ctx.enqueue`, claimed by the worker through `kernel.claim_jobs()`, retried with backoff). A job or event that runs out of attempts raises JOB_FAILURE or EVENT_FAILURE, owned by whoever queued it; retrying from the queue resolves it on success. Modules raise their own exceptions with `raiseException`.
- File service (K-08), ported from Majimap's attachments (done in A10): `kernel.file` plus S3-compatible storage (`kernel/storage.ts`, memory store in development and tests). A device announces a file with an id it minted (a repeat returns the same file), PUTs the bytes to a presigned URL, and confirms; the server checks the size in storage. Keys start with the organization id. Limits per record, under a lock. GPS and capture time per file (W-02). A module registers what files attach to with `defineFileSubject({ kind, module, limits, authorize })` in `kernel/file-subjects.ts`; `authorize` decides read, add and remove, so the kernel never reads module tables.
- Notification service interface (K-07, done in A10): `ctx.notify({ to, channels, topic, title, body, link, template, data, dedupeKey })`, or `notify(tx, …)` from jobs and consumers. In-app goes to `kernel.notification`, the member's inbox (deleted when they leave; the web header bell). SMS, email, push and WhatsApp go out as `notification.requested` for the Communications module (Phase 7), only while it is licensed; a channel that cannot be used comes back in `skipped`, never as an error. The kernel notifies an exception's new owner, whoever queued a job that failed, and the requester when an approval is decided.
- Hierarchy (K-02, done in A3): `kernel.area` (scheme, zone, sub-zone, DMA; a parent sits at any higher level, so unused levels are skipped) and `kernel.route` (route groups and routes), archived rather than deleted. Accounts places service points on routes in Phase 3; GIS adds map data to the kernel's DMA ids in Phase 2.
- Work registry (done in A12): the ports through which modules contribute work-order kinds, asset and evidence resolvers, branch guards, annotators and effects without importing each other, adopted from Majimap's `kernel/ports.ts` and `registry.ts` (`packages/api/src/kernel/work/`). Ports take the tenant transaction and Flowless permissions; a reserved branch prefix without its guard refuses writes; lookups take the licensed modules. `WorkKindDef` adds `capture`, `evidence`, `completionEvent`, `defaultPriority` and `slaHours`; only GIS and Work Orders may register basic kinds. `workLevel(entitlements)` (shared-types) is none, basic or full. The composition root is `packages/api/src/wiring.ts` (`work`); it also calls every module's `registerKernel(kernel)`, which adds the module's consumers, settings, approval kinds, reports, file subjects and jobs to the kernel's registries, so the kernel imports no module. The registries are live lists, read after wiring: import `consumers`, `reports`, `fileSubjects`, `jobs`, `settings` and `approvals` from `wiring.ts` or the package index, not from the kernel registry files. Order is wiring order (consumers run in it; settings list in it, then each approval's policy); a name, key or type registered twice throws.
- PostGIS in the dev database and in the test container (done in A12): `postgis/postgis:17-3.5-alpine` in docker-compose and Testcontainers (Alpine, like the earlier image, so existing dev volumes keep working), enabled by `0019_postgis.sql`.
- ESLint module-boundary rules.
- Report publish guard (X-04, done in A11): `reportPublishProblems(tx, query)` (`kernel/report-guard.ts`) plans a report's query with `EXPLAIN (VERBOSE, FORMAT JSON)` as the app role and refuses it when any relation in the plan lacks `organization_id` or row-level security (views are expanded, so they are covered), when it calls a SECURITY DEFINER function, or when the app role cannot plan it (the `auth` schema). Reports are `defineReport({ key, module, params, query })`, registered with `kernel.report(...)` from the module's `registerKernel` (list in `kernel/report-registry.ts`); CI checks every registered report. The reporting module (X-01) calls the guard when a report definition is published.

**Done when:**

- The isolation canary test passes (NF-02): with two tenants seeded, every procedure run as tenant A returns zero tenant B identifiers.
- Turning off a module unmounts its router and consumers, and the other modules keep working (NF-31).
- A failing job shows up in the exception queue.

### Phase 2: Work Orders core and GIS

Brought forward from the old Phases 9 and 10 and ported from Majimap (`majimap-v2`), which was built to become this module. Neither depends on accounts or billing: other modules add their own work kinds when they ship.

**Scope:** W-01 (generic and GIS kinds), W-02, W-03 (framework), W-04 (S), G-01 to G-03, K-02 map data, U-02 (the work-order half). NFRs: NF-41.

**Code:** `packages/network` (pure graph traces), `modules/work-orders`, `modules/gis`, `packages/db` (`work_orders` and `gis` schemas), web screens and map, `apps/mobile` (ported from Majimap's field app, Expo 58).

**Deliverables:**

- One work-order lifecycle for every kind: pending, in progress (started by the assignee's first action), blocked, submitted, completed, cancelled; review policy none, optional or required per kind, overridable per organization (K-10); parent jobs finalized by a supervisor; idempotent, replayable actions with client-minted ids for offline devices.
- Kinds are registered in code by the module that owns them, with a target (asset, route of assets, area, location, customer), a review policy, required evidence (photo, GPS), a capture schema for completion data, and the event completion publishes (W-03).
- Crews, scheduling, priority and SLA, with breaches in the exception queue (W-02, X-02). Seeing every job needs `work_orders:read`; members who only execute see their own.
- GIS: network assets (nodes, pipes, structures, service connections), tiers, subnetworks, condition and valve logs, traces (directional, isolation, DMA membership). Edits are versioned on branches and posted to main through a field-level three-way merge with integrity checks; deletes are tombstones.
- GIS functions are work kinds: logs (leak, inspection, valve exercise route, flushing, PRV adjustment, facility service, leak survey), edits (valve replacement, asset update) and creates (asset capture, connection capture). A job's edits live on its branch `wo-<code>` and are posted after approval.
- Work-order level: GIS licensed alone gives the GIS kinds; Work Orders licensed adds crews, SLA and other modules' kinds; with neither, dependent features fall back to office action (NF-31).
- Field app: offline store, queued sync with per-item status, job screens, map, asset and connection capture.
- Data foundation (done in W1): `gis` and `work_orders` Postgres schemas with RLS on every table, per-schema grants (`0021`, `0022`), composite tenant foreign keys, GiST indexes on every geometry column, and the structure-attachment trigger (`0023`). Geometry helpers ported to `packages/db/src/geometry.ts`. Work orders reference assets as `(module, asset_id)` without foreign keys, and gain crews, comments, GPS on events and captures; logs and job history are append-only. Permissions `work_orders:review`/`cancel` and `gis:*`, and the `gis_engineer` role.
- Work Orders core (done in W2): `modules/work-orders` ported from Majimap (state machine, rules, store with idempotent replay of client-minted event ids, contents, reads) on `moduleProcedure(["work-orders", "gis"])`, with permissions for roles, scope restrictions, crews, comments, GPS on events, capture and evidence checks, the outbox events (`work_order.created`, `.assigned`, `.status_changed`, `.completed` and each kind's completion event), audit on every change, a notification on assignment, the per-organization review and SLA policy (`work-orders.kind_policy`) and SLA breaches in the exception queue (`WORK_ORDER_OVERDUE`, swept by the worker through `work_orders.overdue_work_orders`). Registers the kinds `repair`, `inspection_general`, `survey`, the `wo-` branch guard and annotator, the asset-work lookup and the `work_order` file subject. Multi-level review through K-05 is left for later.

## UI track (runs alongside the phases)

The staff web UI is built ahead of the backend so it can be used for testing. It never starts a backend phase early: it only consumes contracts.

- **Contracts first.** Screen data types live in `shared-types` (`Money`, `ExceptionItem`, `AccountSummary`, `StatementLine`, ...), the same shapes the procedures will return.
- **One seam per screen.** `apps/web/src/data/<area>.ts` exposes one async function per screen. Until the procedure exists it returns typed fixtures from `apps/web/src/mocks/`; the PR that ships the procedure swaps the body for the tRPC call. Fixtures follow the domain rules: money in minor units, derived values (running balance, previous reading) computed, never stored.
- **Design system.** Tokens and fonts in `apps/web/src/app/globals.css` and `layout.tsx` (ui-ux-pro-max palette, Inter + Geist Mono). Components follow the apple-design skill (instant press feedback, interruptible springs on gesture-driven surfaces, reduced motion, transparency and contrast preferences).
- **Claims:** NF-40 and NF-42 for the web shell and screens, NF-33 for money/date formatting. Each is completed by the phase that ships the matching backend.
