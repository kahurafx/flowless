# Flowless: Build Plan

This plan says **when** each requirement is built and **where in the code** it lives. **What** each ID means is in [requirements.md](requirements.md); that file is the source of truth for behaviour.

A phase is done only when its **Done when** checks pass in CI. Do not start the next phase on red tests.

## Code layout

Flowless is a modular monolith in one pnpm + Turborepo repo. Every module is a folder with a hard boundary, not a separate service (NF-30).

```
apps/
  web/              Next.js: staff UI and portal. Hosts the tRPC HTTP handler at
                    src/app/api/trpc/[trpc]/route.ts and Better Auth at /api/auth/[...all]
                    (Phase 1). Server code calls procedures in-process.
  mobile/           Expo: technician app (U-02). tRPC client only; imports `type AppRouter`.
  worker/           Node process (added in Phase 1): outbox dispatcher, event consumers and
                    queued jobs (billing runs, imports, reconciliation, messaging) (NF-12).
packages/
  api/              tRPC. The only place procedures live.
    src/
      trpc.ts       initTRPC, context (session, organization_id, scopes, entitlements),
                    base procedures: publicProcedure, tenantProcedure, moduleProcedure(module)
      root.ts       appRouter: one key per module router; `export type AppRouter`
      kernel/       tenancy, rbac, entitlements, workflow, audit, outbox, config, files,
                    notifications, exceptions. Always on.
      modules/
        <module>/
          router.ts   tRPC procedures: input validation, then a call into service.ts
          service.ts  use cases; the only code that touches this module's tables
          events.ts   events this module publishes and the consumers it registers
          index.ts    the module's published interface: what other modules may import
  billing-engine/   Pure library (Phase 3): pricing, scaling, estimate, true-up, validators,
                    rollover, void, correct, final bill. No I/O, no DB, no clock.
  db/               Drizzle: client, one schema file per module (each in its own Postgres
                    schema), migrations, RLS policies, withTenant(organizationId, fn).
                    src/schema/auth.ts is generated by Better Auth and exported only as
                    @flowless/db/auth-schema.
  auth/             Better Auth (organization + twoFactor plugins): users, sessions,
                    organizations, members, invitations, MFA, sign-in rate limits (NF-05).
                    Owns the `auth` Postgres schema. Used by the api context to resolve the
                    session; holds no tRPC procedures.
  shared-types/     Platform-neutral types used by web and mobile (IDs, Money, enums).
  eslint-config/, typescript-config/   shared tooling.
```

### Identity and tenancy

Better Auth is the identity layer, and its `organization` table is the tenant table: every `organization_id` in a module schema references `auth.organization.id` (UUIDs).

| Concern | Owner |
| --- | --- |
| Users, sessions, passwords, MFA, sign-in rate limits (NF-05) | Better Auth core and `twoFactor` |
| Organizations, members, invitations, member roles, the session's active organization (K-01, K-03) | Better Auth `organization` plugin. One membership per user (unique index on `auth.member.user_id`); the active organization is set from it when the session is created and cannot be switched. |
| Sign-in by organization code: email for owners and admins, `<code>.<username>` for other staff (requirements §1) | `packages/auth` sign-in hook and Better Auth `username` plugin |
| Role permissions, such as "can approve a rebate" (K-03) | Better Auth access control (`createAccessControl`) with Flowless permission statements |
| Per-scope restrictions by scheme, zone or route (K-03) | Kernel tables. Better Auth roles do not restrict data. |
| Module licensing (K-04), hierarchy (K-02), audit (K-06), support access (K-12) | Kernel. Better Auth hooks feed audit records and publish organization lifecycle events. |

Request flow: `createContext` resolves the Better Auth session from the request headers. `tenantProcedure` takes `session.activeOrganizationId` (rejecting a session without one) and opens `withTenant` with it. RLS still decides what each query sees.

Module folder names (one per entry in requirements §3): `accounts` (customers, accounts, service points), `tariffs`, `metering`, `billing`, `payments`, `communications`, `collections`, `work-orders`, `inventory`, `gis`, `nrw`, `portal`, `reporting`, `migration`, and later `finance`.

### Boundary rules

These rules turn the CLAUDE.md rules into code. Each one is enforced by a check, not by review alone.

| Rule | Enforced by |
| --- | --- |
| The `auth` schema is the one exception to tenant RLS: Better Auth must work before any tenant is known (sign-in, invitations). It is isolated by role instead: `flowless_auth` reaches only `auth`, `flowless_app` never does, and only `packages/auth` imports `@flowless/db/auth-schema`. Modules learn about organizations through events, never by reading `auth.*`. | per-schema grants in migrations; role-separation tests; ESLint import ban outside `packages/auth` |
| Every request runs inside `withTenant`. That sets `app.organization_id` for the transaction, and RLS does the rest (K-01, NF-01). No procedure or job gets the raw connection. | `tenantProcedure`, the app DB role without `BYPASSRLS`, isolation canary test (NF-02) |
| Every module procedure checks the module's entitlement on the server (K-04, NF-03). | `moduleProcedure(module)` is the only builder module routers may use |
| A module imports only its own `@flowless/db` schema file. To reach another module it uses that module's `index.ts` or an event (NF-30). | ESLint `no-restricted-imports` per module folder; per-module Postgres schemas with grants |
| A module that is not licensed has no router mounted for that tenant and no consumers running for it (NF-31). | module-combination matrix test in CI |
| Money is `bigint` minor units plus currency (B-18). It crosses the wire through a tRPC transformer that supports `bigint`. | `Money` type in `shared-types`; no `number` money fields in schemas |
| Ledger, readings and invoices are insert-only (NF-22). | DB grants (no `UPDATE`/`DELETE` on those tables for the app role), tests |
| Heavy work is enqueued from a procedure and run by `apps/worker` (NF-12). Every failure becomes a row in the exception queue with owner and age (NF-24). | kernel job runner wraps every job; no bare `try/catch` that swallows |
| `apps/mobile` never imports runtime code from `@flowless/api`; it imports types only. | `import type` lint rule in mobile |

## Phases

Each phase lists the requirement IDs it owns. An ID is owned by exactly one phase; a later phase that extends it says so.

### Phase 0: Foundations

**Scope:** repo, CI, lint, typecheck, Docker Compose (Postgres, Redis), migration tool (drizzle-kit), Vitest with Testcontainers, seeded two-tenant fixtures.

**Deliverables:**

- `packages/db`: client, `withTenant`, runtime roles (`flowless_app`, `flowless_auth`), Better Auth's generated `auth` schema, and the first tenant-scoped table (`kernel.organization_settings`) with its RLS policy.
- `packages/auth`: Better Auth config (`createAuth`) used to generate the `auth` schema. No routes yet.
- `packages/api`: `trpc.ts` (superjson transformer, `tenantProcedure` running each procedure inside `withTenant`) and `root.ts` with `health` (public, no tenant data) and `organization.settings` (tenant-scoped).
- `apps/web`: tRPC route handler.
- Root `test` task in Turbo.
- GitHub Actions pipeline running lint, check-types and test.

**Done when:**

- CI runs unit and integration tests, including a hello-world RLS test (tenant A's session cannot read tenant B's row) and role-separation tests (the app role cannot read `auth`, the auth role cannot read module schemas).
- `health` answers end to end from web to api to db.
- A fresh clone runs with one command (`pnpm install && pnpm bootstrap`).

### Phase 1: Kernel

**Scope:** K-01 to K-12, X-02, X-04. NFRs: NF-01, NF-02, NF-03, NF-07, NF-24, NF-30, NF-31, NF-32.

**Code:** `packages/api/src/kernel/*`, `packages/auth`, `packages/db` (kernel schema), `apps/worker` (new).

**Deliverables:**

- Better Auth wired up: secret and base URL from env, handler at `/api/auth/[...all]` in web, `@better-auth/expo` for mobile, access-control statements, audit hooks (K-06), organization lifecycle events.
- `createContext` resolves the Better Auth session; `tenantProcedure` uses its `activeOrganizationId` and rejects sessions without one.
- Scope restrictions (K-03) and support access (K-12) as kernel tables on top of Better Auth roles.
- `tenantProcedure` and `moduleProcedure` builders as the entitlement guard for routes and reports.
- Generic approval engine.
- Audit log.
- Outbox, with a dispatcher in `apps/worker`.
- Idempotent event consumer helper, with a `replay` flag.
- Configuration store.
- Exception queue (X-02 framework) fed by the job runner (NF-24).
- File service.
- Notification service interface.
- ESLint module-boundary rules.
- Report publish guard (X-04).

**Done when:**

- The isolation canary test passes (NF-02): with two tenants seeded, every procedure run as tenant A returns zero tenant B identifiers.
- Turning off a module unmounts its router and consumers, and the other modules keep working (NF-31).
- A failing job shows up in the exception queue.

### Phase 2: Foundation domain

**Scope:** C-01 to C-12, T-01 to T-03, T-07 to T-10. These cover customers, accounts with check-digit numbers and parent/child links, service points, the two status axes, activation gates, tariffs with effective dates, the charge catalog, and invoice types and terms.

**Code:** `modules/accounts`, `modules/tariffs`, matching `packages/db` schemas.

**Deliverables:**

- Account state machine.
- Commands with reason and actor.
- Configurable status-by-charge table.
- Charge catalog.
- Tariff versions.
- Data-quality dashboards.

Activation gates that depend on later modules work by office checklist until those modules exist. The meter-installed gate is satisfied through Work Orders and Inventory in Phase 9, and the initial-reading gate through Metering in Phase 4.

**Done when:**

- An account can go from enquiry to `ACTIVE` through configurable gates, with Work Orders and Inventory off.
- A tariff change effective next period is stored as a new version.
- Stale `NEW` or `PENDING_PAYMENT` accounts appear in the exception queue.

### Phase 3: Billing engine and sub-ledger (reference-driven)

**Scope:** B-05, B-06, B-08 to B-11, B-18, T-04, T-05, and requirements §6. NFRs: NF-22, NF-60.

**Code:**

- `packages/billing-engine` (new). The pure engine; it depends on nothing but `shared-types`.
- `modules/billing` and the billing schema in `packages/db`. These hold the sub-ledger and call the engine.

**Deliverables:**

- The engine as a pure library: tariff pricing with scaling policy, estimate and true-up, validators, rollover, void, correct, final bill, credit-note rule.
- Sub-ledger tables: append-only, double-entry, with dimensions, and with `service_from` and `service_to` on lines.

[billing-engine.html](billing-engine.html) is the reference implementation, and its test suite is the starting point for this one.

**Done when:**

- Scenarios S-1 to S-10, invariants I-1 to I-8, and every test in `billing-engine.html` pass as Vitest tests.
- A fast-check property test of at least 200 runs confirms that a span's total does not depend on the estimate path (I-7).
- The engine package has no I/O imports. A lint rule bans `@flowless/db`, `node:*` and network libraries there.

### Phase 4: Metering, readings and billing runs

**Scope:** M-01 to M-12, B-01 to B-04, B-07, B-12 to B-17, B-19, T-06, X-01, X-03. NFRs: NF-11, NF-12, NF-13.

**Code:** `modules/metering`, `modules/billing` (runs), `modules/reporting`, jobs in `apps/worker`.

**Deliverables:**

- Meter register and installations.
- Append-only readings with a derived previous reading.
- Validation, with exception queues.
- One eligibility snapshot shared by reading tasks and billing.
- Outcome-to-disposition mapping.
- Estimation policy runner.
- Bill-on-reading and the batch cycle as a job per account.
- Completeness check.
- Disconnection and reconnection commands.
- Late-reading correction documents with a grace window.
- Period lock.
- Statements with typed lines.
- Tariff simulation.
- Report definitions over read models, and CSV/Excel export.

**Done when:**

- A cycle cannot close with unexplained accounts.
- Every legacy failure mode the requirements name has a test.
- Billing a seeded tenant of 100,000 accounts meets NF-11.

### Phase 5: Payments

**Scope:** P-01 to P-11. NFRs: NF-04, NF-20, NF-23.

**Code:** `modules/payments`. Provider callbacks are tRPC-free HTTP route handlers in `apps/web` that only enqueue. Processing runs in `apps/worker`.

**Deliverables:**

- Immutable payment events.
- Matching on account number.
- Allocation.
- Payment state machine.
- Suspense queue.
- Provider adapters (M-Pesa, one bank, card) behind one interface.
- Polling backstop.
- Statement import.
- Three-way reconciliation.
- Claim by transaction code.

**Done when:**

- Polling recovers a dropped callback.
- An unmatched payment is visible and can be resolved.
- Reconciliation produces typed exceptions.

### Phase 6: Communications

**Scope:** N-01 to N-07. Implements the K-07 interface from Phase 1.

**Code:** `modules/communications`.

**Deliverables:**

- Message records with a unique key.
- Provider receipts.
- Retries.
- Fallback queue for missing or placeholder numbers.
- Campaign view.
- SMS wallet.
- Delivery-confirmed charges (off by default).

**Done when:**

- Re-running a campaign never sends a duplicate.
- Every account without a message is listed with a reason.

### Phase 7: Import and migration

**Scope:** Q-01 to Q-10. NFRs: NF-61.

**Code:** `modules/migration`, import jobs in `apps/worker`.

**Deliverables:**

- Import pipeline: upload, staging, validation, error report, dry-run, chunked commit, rollback by batch ID.
- Tiers A, B and C.
- Per-account reconciliation gate.
- `NO_BASELINE` hold.
- Legacy-variance lines.

**Done when:**

- A sample legacy export imports idempotently.
- Balances reconcile.
- A parallel-run report compares legacy and Flowless.

### Phase 8: Technician app and customer portal

**Scope:** U-01 to U-04. It extends M-03 (mobile and portal reading sources) and M-11. NFRs: NF-14, NF-41, NF-42.

**Code:**

- `apps/mobile`: Expo Router and an offline store.
- `modules/portal`.
- Portal routes in `apps/web`.
- The landing page as a static route that does not depend on `@flowless/api`.

**Deliverables:**

- Offline-first reading tasks per route, with outcome, photo and GPS.
- Sync with conflict rules.
- Portal with bills, statements, STK pay, self-reading, claims and complaints.

**Done when:**

- A technician syncs a full route after a day offline, with no lost or duplicate readings.

### Phase 9: Collections, Work Orders, Inventory

**Scope:** D-01 to D-06, W-01 to W-04, I-01 to I-05. This phase also wires the C-05 and C-06 gates that wait on work orders and inventory.

**Code:** `modules/collections`, `modules/work-orders`, `modules/inventory`.

**Done when:**

- Disconnection, meter install and meter change flow end to end through events.
- The nightly check across status, connection and meter location raises exceptions.
- Accounts with commitments in good standing never appear in disconnection lists.

### Phase 10: GIS, NRW, then Finance and GL

**Scope:** G-01 to G-03, R-01, R-02, then the GL module from requirements §5.

**Code:** `modules/gis`, `modules/nrw`, `modules/finance`.

**Done when:**

- GL consumes events idempotently.
- The sub-ledger total equals the GL AR control account.

## UI track (runs alongside the phases)

The staff web UI is built ahead of the backend so it can be used for testing. It never starts a backend phase early: it only consumes contracts.

- **Contracts first.** Screen data types live in `shared-types` (`Money`, `ExceptionItem`, `AccountSummary`, `StatementLine`, ...), the same shapes the procedures will return.
- **One seam per screen.** `apps/web/src/data/<area>.ts` exposes one async function per screen. Until the procedure exists it returns typed fixtures from `apps/web/src/mocks/`; the PR that ships the procedure swaps the body for the tRPC call. Fixtures follow the domain rules: money in minor units, derived values (running balance, previous reading) computed, never stored.
- **Design system.** Tokens and fonts in `apps/web/src/app/globals.css` and `layout.tsx` (ui-ux-pro-max palette, Inter + Geist Mono). Components follow the apple-design skill (instant press feedback, interruptible springs on gesture-driven surfaces, reduced motion, transparency and contrast preferences).
- **Claims:** NF-40 and NF-42 for the web shell and screens, NF-33 for money/date formatting. Each is completed by the phase that ships the matching backend.

## Unassigned

NF-05, NF-06, NF-10, NF-21, NF-33 (formatting started in the UI track), NF-50 to NF-53 and NF-62 are cross-cutting. Each is picked up by the first phase that needs it; for example, NF-05 lands with `packages/auth` in Phase 1. Record the owning phase here when a phase claims one.
