# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## `@flowless/api`

Reference /trpc skill.

The tRPC layer: every procedure in Flowless lives here. Phase 0 scaffold: `trpc.ts` (superjson, `tenantProcedure`), `root.ts` (`health`, `organization.settings`), `http.ts` (`createTrpcHandler({ endpoint, getDb, getSession })`). `Session` is the narrow slice of `Caller` (from `@flowless/auth`: Better Auth session plus the current membership) the API uses; `tenantProcedure` takes `session.activeOrganizationId` (UNAUTHORIZED without a session, FORBIDDEN without an active organization or when `session.member` is missing or elsewhere) and exposes `ctx.organizationId`, `ctx.role`, `ctx.permissions` (role defaults plus `kernel.member_permission` grants, K-03) and `ctx.tx`. Guard actions with `permittedProcedure("<resource>:<action>")`; the catalogue and default roles are in `@flowless/shared-types` permissions. `ctx.scope()` (lazy, `kernel/scope.ts`) is the member's scope restriction, `all` or `limited` area and route ids expanded to everything below. `kernel/access.ts`: `access.me` (role, permissions, scope), `access.grants`, `access.grant`, `access.revoke`, `access.scopes`, `access.setScope` (a limited manager gives only scope inside their own, never unrestricted). `kernel/hierarchy.ts` (K-02): `hierarchy.areas`/`routes` for everyone; create, update, archive and restore need `settings:manage`. Events (K-09): define with `defineEvent(type, zodSchema, version)` in the module's `events.ts`, publish with `ctx.publish(event, payload, { id? })` in the change's transaction, consume with `defineConsumer({ name, module, event, handle })` registered in `kernel/consumers.ts`. Consumers run once per event (receipts) inside the event's tenant and must be idempotent; on `replay: true` skip effects outside the database. `dispatchOutbox`, `drainOutbox` (tests, seeds) and `replayEvents` are in `kernel/events.ts`. Jobs (NF-12): `defineJob({ type, module, label, schema, run })` registered in `kernel/job-registry.ts`, queued with `ctx.enqueue(job, payload, { idempotencyKey?, runAt? })`; `run` writes through `ctx.withTenant` per unit of work, calls `ctx.heartbeat()` on long runs, and must be safe to run again. Exceptions (X-02, NF-24): raise with `raiseException(tx, organizationId, { type, source, title, subject, areaId?, routeId?, ownerUserId?, dedupeKey? })` from `kernel/exception-store.ts`; `exceptions.list` needs `exceptions:read`, `assign`/`start`/`resolve`/`reopen`/`retry` need `exceptions:resolve`, and scope applies. Every change writes `ctx.audit({ action, subjectType, subjectId, before, after })` (K-06) in the same transaction; skip it when nothing changed. `Context.source` (web, mobile, api, import, system) comes from the `x-flowless-client` header in `http.ts`, or is set by in-process callers. `audit.list` and `audit.verify` need `audit:read`. `setEntitlements` audits as a system action. `moduleProcedure(module, ...permissions)` is the builder for module routers: licence first (NOT_FOUND when unlicensed), then permissions; `ctx.entitlements()` is lazy. `entitlements.list` for everyone; `setEntitlements(db, organizationId, modules)` (exported, server-side only, never a procedure) is how Flowless licenses an organization. Keep `kernel/entitlement-store.ts` free of `../trpc` imports, since `trpc.ts` imports it. Configuration (K-10, NF-32): define with `defineSetting({ key, module, label, description, schema, default })` (`kernel/config-store.ts`; the schema must keep reading every stored version, so add fields with `.default()`), register in `kernel/config-registry.ts`, read with `ctx.config(setting, at?)` or `readSetting(tx, setting, at)`. `config.list`/`history`/`set` need `settings:manage`; `set` takes `expectedVersion` (CONFLICT when stale) and an optional future `effectiveFrom`, and writes nothing when the value is unchanged. `organization.settings` returns currency plus `kernel.regional` (time zone, language). Keep `kernel/config-store.ts` free of `../trpc` imports. Approvals (K-05): `defineApproval({ key, module, label, description, reasonCodes, policy })` in `kernel/approval-store.ts`, registered in `kernel/approval-registry.ts` (which adds its policy setting `approvals.<key>` to the config registry); ask with `ctx.requestApproval(kind, { subjectRef, title, amount?, reasonCode?, note?, payload?, areaId?, routeId? })` (audited; `approved` at once when no level applies; CONFLICT if one is already pending for the subject); apply outcomes with `defineApprovalConsumer(kind, name, handle)` in `kernel/consumers.ts`. `approvals.list`/`get`/`approve`/`reject`/`cancel` need no extra permission: a member sees requests they made, decided or could decide at some level, within scope, and `decideProblem` enforces the level permission, no self-approval and one level per person. `escalateApprovals(db)` runs in the worker. Files (K-08): `files.announce` (client-minted id, returns a presigned PUT), `confirm` (checks the size in storage; a mismatch returns `problem` and removes the file), `list` (presigned GET URLs) and `remove`; access is the subject's `authorize` from `defineFileSubject` in `kernel/file-subjects.ts`. Notifications (K-07): `ctx.notify(input)` / `notify(tx, organizationId, input)` in `kernel/notification-store.ts` returns `{ sent, skipped }`; `notifications.list`/`unreadCount`/`markRead` are the caller's own inbox. Support access (K-12): `support.list`/`grant`/`revoke` need `access:manage`; `supportSession({ organizationId, grantId, engineer })` (server-side only, never from HTTP) builds a `Session` with `member: null` and `support.grantId`; `tenantProcedure` then requires a live grant for that engineer, allows queries only, limits permissions to the grant's read permissions, writes `support.read` per call and `support.refused` (in its own transaction) for refused ones. `ctx.audit` uses the support actor automatically. Reports (X-01, X-04): `defineReport({ key, module, label, params, query })` in `kernel/report-guard.ts`, registered in `kernel/report-registry.ts`; `reportPublishProblems(tx, query)` must return `[]` before a report is published (it trusts the query plan, not the report). `Context.storage` overrides the environment's storage (tests pass `createMemoryStorage().storage`). Map Postgres errors with `kernel/pg-errors.ts`. Tests share `src/test-support.ts` (`addMember`, `sessionOf`, `callerFor`). Apps read error messages with `clientErrorMessage`, never by importing `@trpc/server`. Target layout and boundary rules are in `docs/build-plan.md` → "Code layout". Shared package conventions are in the root `CLAUDE.md`.

- Work registry (W-01, adopted from Majimap): ports and `WorkRegistry` in `kernel/work/`; modules register adapters and work kinds (`defineWorkKind`) on `work` in `src/wiring.ts` from their `index.ts`, never by importing each other. Tests build their own `new WorkRegistry()`.
- Mount a module router in `root.ts` at the camelCase of its module key (`workOrders` for `work-orders`); `src/module-matrix.test.ts` relies on it and lists the kernel routers. `test-support.ts` has `procedures()` and `callPath()` for tests that walk every endpoint. Adding a procedure means adding its calls to `CALLS` in `src/isolation-canary.test.ts` (aim id inputs at tenant B's records); a new tenant table must be seeded for B in that test's `seedB`.
- Layout: `src/trpc.ts` (context and base procedures), `src/root.ts` (`appRouter`, `export type AppRouter`), `src/kernel/*`, `src/modules/<module>/{router,service,events,index}.ts`.
- Module routers build procedures only from `moduleProcedure(module)`. That runs `withTenant` (RLS) and the entitlement check. Never use the raw DB client.
- A module touches only its own `@flowless/db` schema. It reaches other modules through their `index.ts` or through events.
- Long-running work is enqueued for `apps/worker`; procedures never run billing, imports or reconciliation inline.
- Server-only package (Node). `apps/web` imports it at runtime. `apps/mobile` may only `import type { AppRouter }`.
- No build step: consumers import `src/index.ts` directly via `exports`. Scripts: `pnpm lint`, `pnpm check-types` (or `pnpm turbo run check-types --filter=@flowless/api`).
