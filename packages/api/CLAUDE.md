# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## `@flowless/api`

Reference /trpc skill.

The tRPC layer: every procedure in Flowless lives here. Phase 0 scaffold: `trpc.ts` (superjson, `tenantProcedure`), `root.ts` (`health`, `organization.settings`), `http.ts` (`createTrpcHandler({ endpoint, getDb, getSession })`). `Session` is the narrow slice of `Caller` (from `@flowless/auth`: Better Auth session plus the current membership) the API uses; `tenantProcedure` takes `session.activeOrganizationId` (UNAUTHORIZED without a session, FORBIDDEN without an active organization or when `session.member` is missing or elsewhere) and exposes `ctx.organizationId`, `ctx.role`, `ctx.permissions` (role defaults plus `kernel.member_permission` grants, K-03) and `ctx.tx`. Guard actions with `permittedProcedure("<resource>:<action>")`; the catalogue and default roles are in `@flowless/shared-types` permissions. `ctx.scope()` (lazy, `kernel/scope.ts`) is the member's scope restriction, `all` or `limited` area and route ids expanded to everything below. `kernel/access.ts`: `access.me` (role, permissions, scope), `access.grants`, `access.grant`, `access.revoke`, `access.scopes`, `access.setScope` (a limited manager gives only scope inside their own, never unrestricted). `kernel/hierarchy.ts` (K-02): `hierarchy.areas`/`routes` for everyone; create, update, archive and restore need `settings:manage`. Events (K-09): define with `defineEvent(type, zodSchema, version)` in the module's `events.ts`, publish with `ctx.publish(event, payload, { id? })` in the change's transaction, consume with `defineConsumer({ name, module, event, handle })` registered with `kernel.consumer(...)` in the module's `registerKernel`. Consumers run once per event (receipts) inside the event's tenant and must be idempotent; on `replay: true` skip effects outside the database. `dispatchOutbox`, `drainOutbox` (tests, seeds) and `replayEvents` are in `kernel/events.ts`. Jobs (NF-12): `defineJob({ type, module, label, schema, run })` registered with `kernel.job(...)` in the module's `registerKernel`, queued with `ctx.enqueue(job, payload, { idempotencyKey?, runAt? })`; `run` writes through `ctx.withTenant` per unit of work, calls `ctx.heartbeat()` on long runs, and must be safe to run again. Exceptions (X-02, NF-24): raise with `raiseException(tx, organizationId, { type, source, title, subject, areaId?, routeId?, ownerUserId?, dedupeKey? })` from `kernel/exception-store.ts`; `exceptions.list` needs `exceptions:read`, `assign`/`start`/`resolve`/`reopen`/`retry` need `exceptions:resolve`, and scope applies. Every change writes `ctx.audit({ action, subjectType, subjectId, before, after })` (K-06) in the same transaction; skip it when nothing changed. `Context.source` (web, mobile, api, import, system) comes from the `x-flowless-client` header in `http.ts`, or is set by in-process callers. `audit.list` and `audit.verify` need `audit:read`. `setEntitlements` audits as a system action. `moduleProcedure(module, ...permissions)` is the builder for module routers: licence first (NOT_FOUND when unlicensed), then permissions; `ctx.entitlements()` is lazy. A router several modules bring passes a list (`moduleProcedure(["work-orders", "gis"])`) and answers while ANY is licensed; finer gates (such as `workLevel`) are the router's own, and `module-matrix.test.ts` maps the router key to the list (`SHARED`). `entitlements.list` for everyone; `setEntitlements(db, organizationId, modules)` (exported, server-side only, never a procedure) is how Flowless licenses an organization. Keep `kernel/entitlement-store.ts` free of `../trpc` imports, since `trpc.ts` imports it. Configuration (K-10, NF-32): define with `defineSetting({ key, module, label, description, schema, default })` (`kernel/config-store.ts`; the schema must keep reading every stored version, so add fields with `.default()`), register with `kernel.setting(...)` in the module's `registerKernel`, read with `ctx.config(setting, at?)` or `readSetting(tx, setting, at)`. `config.list`/`history`/`set` need `settings:manage`; `set` takes `expectedVersion` (CONFLICT when stale) and an optional future `effectiveFrom`, and writes nothing when the value is unchanged. `organization.settings` returns currency plus `kernel.regional` (time zone, language). Keep `kernel/config-store.ts` free of `../trpc` imports. Approvals (K-05): `defineApproval({ key, module, label, description, reasonCodes, policy })` in `kernel/approval-store.ts`, registered with `kernel.approval(...)` in the module's `registerKernel` (which adds its policy setting `approvals.<key>` to the config registry); ask with `ctx.requestApproval(kind, { subjectRef, title, amount?, reasonCode?, note?, payload?, areaId?, routeId? })` (audited; `approved` at once when no level applies; CONFLICT if one is already pending for the subject); apply outcomes with `defineApprovalConsumer(kind, name, handle)`, registered with `kernel.consumer(...)`. `approvals.list`/`get`/`approve`/`reject`/`cancel` need no extra permission: a member sees requests they made, decided or could decide at some level, within scope, and `decideProblem` enforces the level permission, no self-approval and one level per person. `escalateApprovals(db)` runs in the worker. Files (K-08): `files.announce` (client-minted id, returns a presigned PUT), `confirm` (checks the size in storage; a mismatch returns `problem` and removes the file), `list` (presigned GET URLs) and `remove`; access is the subject's `authorize` from `defineFileSubject` in `kernel/file-subjects.ts` (`module` may be a list, found while any is licensed), registered with `kernel.fileSubject(...)`; `photoCounts(tx, subjectKind, ids)` there is the published read of uploaded photos for evidence checks. Notifications (K-07): `ctx.notify(input)` / `notify(tx, organizationId, input)` in `kernel/notification-store.ts` returns `{ sent, skipped }`; `notifications.list`/`unreadCount`/`markRead` are the caller's own inbox. Support access (K-12): `support.list`/`grant`/`revoke` need `access:manage`; `supportSession({ organizationId, grantId, engineer })` (server-side only, never from HTTP) builds a `Session` with `member: null` and `support.grantId`; `tenantProcedure` then requires a live grant for that engineer, allows queries only, limits permissions to the grant's read permissions, writes `support.read` per call and `support.refused` (in its own transaction) for refused ones. `ctx.audit` uses the support actor automatically. Reports (X-01, X-04): `defineReport({ key, module, label, params, query })` in `kernel/report-guard.ts`, registered with `kernel.report(...)`; `reportPublishProblems(tx, query)` must return `[]` before a report is published (it trusts the query plan, not the report). `Context.storage` overrides the environment's storage (tests pass `createMemoryStorage().storage`). Map Postgres errors with `kernel/pg-errors.ts`. Tests share `src/test-support.ts` (`addMember`, `sessionOf`, `callerFor`). Apps read error messages with `clientErrorMessage`, never by importing `@trpc/server`. Target layout and boundary rules are in `docs/build-plan.md` → "Code layout". Shared package conventions are in the root `CLAUDE.md`.

- Composition root (`src/wiring.ts`): the kernel imports no module. Each module's `index.ts` exports `register(work)` (Work Registry adapters and kinds, when it has any) and `registerKernel(kernel: KernelRegistrar)` (`kernel/registrar.ts`: `consumer`, `setting`, `approval`, `report`, `fileSubject`, `job`, each throwing when a name, key or type is registered twice); `wiring.ts` calls them in order (consumers run, and settings list, in that order; approval policy settings come last). The registry lists (`kernel/consumers.ts`, `config-registry.ts`, `approval-registry.ts`, `report-registry.ts`, `file-subject-registry.ts`, `job-registry.ts`) are live and empty until wiring runs, so read them through `wiring.ts` (it re-exports them) or the package index, never from the kernel files; the kernel routers read them per request. A new module adds its lines to `wiring.ts` and touches no kernel file. `wiring.test.ts` pins the wired lists.
- Work registry (W-01, adopted from Majimap): ports and `WorkRegistry` in `kernel/work/`; modules register adapters and work kinds (`defineWorkKind`) on `work` in `src/wiring.ts` from their `index.ts`, never by importing each other. Tests build their own `new WorkRegistry()`.
- Work Orders (`modules/work-orders`, Phase 2 W2, ported from Majimap): `createWorkOrdersRouter(work)` mounted at `workOrders`, procedures from `workOrderProcedures(work)`, pure state machine, device actions through `lockAndReplay`, SLA sweep in the worker. Details: `src/modules/work-orders/CLAUDE.md`.
- GIS (`modules/gis`, Phase 2 W3, ported from Majimap): `createGisRouter(work)` mounted at `gis`, procedures from `gisProcedures(work)`, Majimap's versioning engine as it is (branches, merge, post in a savepoint), logs, reports. Details: `src/modules/gis/CLAUDE.md`.
- Accounts (`modules/accounts`, Phase 3 F1, F3a, F3b, F4, F4b: C-01 to C-12): `accountsRouter` mounted at `accounts` (customers, contacts, service points, accounts, status commands, applications, memberships, succession, relocation, change of name, data quality). `commands.ts` is the only code changing a status; `service.ts` holds the customer, account and service point row finders and DTOs, and each concern has its own file (`contacts.ts`, `duplicates.ts`, `account-numbers.ts`, `placement.ts`). Every client-mintable-id step goes through `idempotent.ts` and every port through `kernel/port-registry.ts`. Procedures, lifecycle, applications, ports, data quality and tests: `src/modules/accounts/CLAUDE.md`.
- Tariffs (`modules/tariffs`, Phase 3 F2: T-01 to T-04): `tariffsRouter` mounted at `tariffs` (tariffs, categories, charge items, invoice types, late-fee simulation). Money is bigint minor units, versions are insert-only, one rule (`chooseEffectiveDate`) dates every change and the closed-period port is Billing's to fill. Published reads (`categoryExists`, `categoriesById`, `categoryPricing`, `tariffVersionInForce`, `chargeItemByCode`, `allocateInvoiceNumber`) are in `index.ts`. Details: `src/modules/tariffs/CLAUDE.md`.
- Billing (`modules/billing`, Phase 4 P4-3: B-10, B-11, B-18, T-04): `billingRouter` mounted at `billing` (usage invoices through the pure engine, credit and debit notes behind the K-05 approval `billing.adjustment`, void, re-bill, derived balance and statement). Only `post.ts` writes documents and ledger entries. Billing cycles (Phase 5 P5-3: B-01 to B-04, B-15, B-16): `billing.cycles.*` (logged state machine, Metering snapshot or Accounts fallback, completeness before close, period lock, review by exception). Details and assumptions: `src/modules/billing/CLAUDE.md`.
- Metering (`modules/metering`, Phase 5 P5-1a and P5-1b: M-01 to M-12): `meteringRouter` mounted at `metering` (meter register and logged lifecycle, bulk and master meters, installations, replacement, append-only readings with validation flags, review, correction, reading attempts with outcomes and dispositions, the per-route eligibility snapshot, derived miss counters and the revisit, prompt, escalation and zero-streak policies, closing-reading handovers). Published reads `readingsFor`, `latestActualReading`, `dispositionFor`, `snapshotFor`, `consecutiveMisses`; it registers the Accounts ports `initial_reading`, `active_metered_no_meter` and the reading handover (all `requires: ["metering"]`). Details and assumptions: `src/modules/metering/CLAUDE.md`.
- Ports between modules (NF-30, NF-31): `kernel/port-registry.ts` is the one helper for process-global port registries. `definePort<T>()` (one handler) and `defineKeyedPort<K, T>()` (one per key) store `{ handler, requires }`; `register(handler | null, { requires })` replaces or removes (tests pass null), `has()` says whether something is registered, and `resolve(tx)` (`resolveAll(tx, keys)` for several keys) returns the handler only while every module in `requires` is licensed for the organization, loading the entitlements lazily and at most once per call. Accounts' gate sources, termination check, balance transfer, reading handover and data-quality sources are built on it; Tariffs' closed-period port (no `requires`, no transaction-bound licence need) and `kernel/work/ports.ts` (the Work Registry's adapters) are separate and unchanged.
- Mount a module router in `root.ts` at the camelCase of its module key (`workOrders` for `work-orders`); `src/module-matrix.test.ts` relies on it and lists the kernel routers. `test-support.ts` has `procedures()` and `callPath()` for tests that walk every endpoint. Adding a procedure means adding its calls to `CALLS` in `src/isolation-canary.test.ts` (aim id inputs at tenant B's records); a new tenant table must be seeded for B in that test's `seedB`, and a new module schema added to its `TENANT_SCHEMAS`.
- Layout: `src/trpc.ts` (context and base procedures), `src/root.ts` (`appRouter`, `export type AppRouter`), `src/kernel/*`, `src/modules/<module>/{router,events,index}.ts` plus one file per use case or concern.
- Use cases take one env, `ActionEnv` from `kernel/action-env.ts` (tx, organizationId, actor, source, `audit`, `publish`): `procedureEnv(ctx)` builds a `UserActionEnv` (actor.userId is a string), `systemEnv(tx, organizationId)` an `ActionEnv` with no user. Take `UserActionEnv` where a person must be recorded; modules import it from the kernel, never from each other.
- Module routers build procedures only from `moduleProcedure(module)`. That runs `withTenant` (RLS) and the entitlement check. Never use the raw DB client.
- A module touches only its own `@flowless/db` schema. It reaches other modules through their `index.ts` or through events.
- Long-running work is enqueued for `apps/worker`; procedures never run billing, imports or reconciliation inline.
- Server-only package (Node). `apps/web` imports it at runtime. `apps/mobile` may only `import type { AppRouter }`.
- No build step: consumers import `src/index.ts` directly via `exports`. Scripts: `pnpm lint`, `pnpm check-types` (or `pnpm turbo run check-types --filter=@flowless/api`).
