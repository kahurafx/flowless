# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## `@flowless/api`

Reference /trpc skill.

The tRPC layer: every procedure in Flowless lives here. Phase 0 scaffold: `trpc.ts` (superjson, `tenantProcedure`), `root.ts` (`health`, `organization.settings`), `http.ts` (`createTrpcHandler({ endpoint, getDb, getSession })`). `Session` is the narrow slice of `Caller` (from `@flowless/auth`: Better Auth session plus the current membership) the API uses; `tenantProcedure` takes `session.activeOrganizationId` (UNAUTHORIZED without a session, FORBIDDEN without an active organization or when `session.member` is missing or elsewhere) and exposes `ctx.organizationId`, `ctx.role`, `ctx.permissions` (role defaults plus `kernel.member_permission` grants, K-03) and `ctx.tx`. Guard actions with `permittedProcedure("<resource>:<action>")`; the catalogue and default roles are in `@flowless/shared-types` permissions. `ctx.scope()` (lazy, `kernel/scope.ts`) is the member's scope restriction, `all` or `limited` area and route ids expanded to everything below. `kernel/access.ts`: `access.me` (role, permissions, scope), `access.grants`, `access.grant`, `access.revoke`, `access.scopes`, `access.setScope` (a limited manager gives only scope inside their own, never unrestricted). `kernel/hierarchy.ts` (K-02): `hierarchy.areas`/`routes` for everyone; create, update, archive and restore need `settings:manage`. Events (K-09): define with `defineEvent(type, zodSchema, version)` in the module's `events.ts`, publish with `ctx.publish(event, payload, { id? })` in the change's transaction, consume with `defineConsumer({ name, module, event, handle })` registered in `kernel/consumers.ts`. Consumers run once per event (receipts) inside the event's tenant and must be idempotent; on `replay: true` skip effects outside the database. `dispatchOutbox`, `drainOutbox` (tests, seeds) and `replayEvents` are in `kernel/events.ts`. Jobs (NF-12): `defineJob({ type, module, label, schema, run })` registered in `kernel/job-registry.ts`, queued with `ctx.enqueue(job, payload, { idempotencyKey?, runAt? })`; `run` writes through `ctx.withTenant` per unit of work, calls `ctx.heartbeat()` on long runs, and must be safe to run again. Exceptions (X-02, NF-24): raise with `raiseException(tx, organizationId, { type, source, title, subject, areaId?, routeId?, ownerUserId?, dedupeKey? })` from `kernel/exception-store.ts`; `exceptions.list` needs `exceptions:read`, `assign`/`start`/`resolve`/`reopen`/`retry` need `exceptions:resolve`, and scope applies. Every change writes `ctx.audit({ action, subjectType, subjectId, before, after })` (K-06) in the same transaction; skip it when nothing changed. `Context.source` (web, mobile, api, import, system) comes from the `x-flowless-client` header in `http.ts`, or is set by in-process callers. `audit.list` and `audit.verify` need `audit:read`. `setEntitlements` audits as a system action. `moduleProcedure(module, ...permissions)` is the builder for module routers: licence first (NOT_FOUND when unlicensed), then permissions; `ctx.entitlements()` is lazy. A router several modules bring passes a list (`moduleProcedure(["work-orders", "gis"])`) and answers while ANY is licensed; finer gates (such as `workLevel`) are the router's own, and `module-matrix.test.ts` maps the router key to the list (`SHARED`). `entitlements.list` for everyone; `setEntitlements(db, organizationId, modules)` (exported, server-side only, never a procedure) is how Flowless licenses an organization. Keep `kernel/entitlement-store.ts` free of `../trpc` imports, since `trpc.ts` imports it. Configuration (K-10, NF-32): define with `defineSetting({ key, module, label, description, schema, default })` (`kernel/config-store.ts`; the schema must keep reading every stored version, so add fields with `.default()`), register in `kernel/config-registry.ts`, read with `ctx.config(setting, at?)` or `readSetting(tx, setting, at)`. `config.list`/`history`/`set` need `settings:manage`; `set` takes `expectedVersion` (CONFLICT when stale) and an optional future `effectiveFrom`, and writes nothing when the value is unchanged. `organization.settings` returns currency plus `kernel.regional` (time zone, language). Keep `kernel/config-store.ts` free of `../trpc` imports. Approvals (K-05): `defineApproval({ key, module, label, description, reasonCodes, policy })` in `kernel/approval-store.ts`, registered in `kernel/approval-registry.ts` (which adds its policy setting `approvals.<key>` to the config registry); ask with `ctx.requestApproval(kind, { subjectRef, title, amount?, reasonCode?, note?, payload?, areaId?, routeId? })` (audited; `approved` at once when no level applies; CONFLICT if one is already pending for the subject); apply outcomes with `defineApprovalConsumer(kind, name, handle)` in `kernel/consumers.ts`. `approvals.list`/`get`/`approve`/`reject`/`cancel` need no extra permission: a member sees requests they made, decided or could decide at some level, within scope, and `decideProblem` enforces the level permission, no self-approval and one level per person. `escalateApprovals(db)` runs in the worker. Files (K-08): `files.announce` (client-minted id, returns a presigned PUT), `confirm` (checks the size in storage; a mismatch returns `problem` and removes the file), `list` (presigned GET URLs) and `remove`; access is the subject's `authorize` from `defineFileSubject` in `kernel/file-subjects.ts` (`module` may be a list, found while any is licensed), registered in `kernel/file-subject-registry.ts`; `photoCounts(tx, subjectKind, ids)` there is the published read of uploaded photos for evidence checks. Notifications (K-07): `ctx.notify(input)` / `notify(tx, organizationId, input)` in `kernel/notification-store.ts` returns `{ sent, skipped }`; `notifications.list`/`unreadCount`/`markRead` are the caller's own inbox. Support access (K-12): `support.list`/`grant`/`revoke` need `access:manage`; `supportSession({ organizationId, grantId, engineer })` (server-side only, never from HTTP) builds a `Session` with `member: null` and `support.grantId`; `tenantProcedure` then requires a live grant for that engineer, allows queries only, limits permissions to the grant's read permissions, writes `support.read` per call and `support.refused` (in its own transaction) for refused ones. `ctx.audit` uses the support actor automatically. Reports (X-01, X-04): `defineReport({ key, module, label, params, query })` in `kernel/report-guard.ts`, registered in `kernel/report-registry.ts`; `reportPublishProblems(tx, query)` must return `[]` before a report is published (it trusts the query plan, not the report). `Context.storage` overrides the environment's storage (tests pass `createMemoryStorage().storage`). Map Postgres errors with `kernel/pg-errors.ts`. Tests share `src/test-support.ts` (`addMember`, `sessionOf`, `callerFor`). Apps read error messages with `clientErrorMessage`, never by importing `@trpc/server`. Target layout and boundary rules are in `docs/build-plan.md` → "Code layout". Shared package conventions are in the root `CLAUDE.md`.

- Work registry (W-01, adopted from Majimap): ports and `WorkRegistry` in `kernel/work/`; modules register adapters and work kinds (`defineWorkKind`) on `work` in `src/wiring.ts` from their `index.ts`, never by importing each other. Tests build their own `new WorkRegistry()`.
- Work Orders (`modules/work-orders`, Phase 2 W2, ported from Majimap): `createWorkOrdersRouter(work)` mounted at `workOrders`, built over a `WorkRegistry` so tests bring their own kinds and resolvers (`test/harness.ts` stands in for GIS so these suites don't depend on its engine). Procedures come from `workOrderProcedures(work)` (`procedures.ts`): `base` (Work Orders or GIS licensed; any work-order permission; adds `ctx.level`, `ctx.licensed`, `ctx.abilities`, `ctx.visibility`), `acting` (`work_orders:execute` or `assign`) and `full` (level full, NOT_FOUND otherwise: crews, `schedule`, SLA). Permissions replace Majimap's roles: execute is "act", assign is "manage" (raise for anyone, act on any visible job, link anyone's logs, write any job branch), `review` approves, returns and finalizes, `cancel` cancels; `work_orders:read` sees every job in scope, otherwise only one's own and one's crews' (`access.ts`, pure). The state machine (`transitions.ts`) and `planCreate` (`rules.ts`) are pure and verbatim; device actions take a client-minted `eventId`, `occurredAt` and `position`, go through `lockAndReplay` and `settle` (`store.ts`): outcomes applied, unchanged, replayed, rejected, stale; an id used elsewhere (other job, person, action or organization) is CONFLICT. Every applied change is audited (`work_orders.<event type>`) and a status move publishes `work_order.status_changed`; also `work_order.created`, `.assigned`, `.completed` (with the capture in force) and the kind's own `completionEvent` with the same payload (`events.ts`). Finishing checks the kind's `evidence` (photos on the job, GPS on the event) and `capture` schema; failures are rejected outcomes, the capture is appended to `work_order_capture`. `workOrders.kinds` also returns each kind's `captureSchema` (the capture form as JSON Schema, null when none) for clients that draw the form. Review and SLA hours per kind are overridable with the `work-orders.kind_policy` setting (`policy.ts`), read at creation. `sweepOverdueWorkOrders(db)` (`sla.ts`) runs in the worker and raises `WORK_ORDER_OVERDUE` once per job (resolved on completion, cancel or a reschedule into the future). `index.ts` exports `register(work)` (kinds `repair`, `inspection_general`, `survey`, the `wo-` branch guard and annotator, the asset-work lookup), called in `wiring.ts`. Multi-level review through approvals (K-05) is not wired yet.
- GIS (`modules/gis`, Phase 2 W3, ported from Majimap): `createGisRouter(work)` mounted at `gis` (nodes, structures, pipes, connections, dmas, tiers, subnetworks, attachmentRules, trace, logs, reconcile, reports). Procedures from `gisProcedures(work)` (`procedures.ts`): `read` (`gis:read`: the network, history, traces, logs, branch list and preview), `edit` (`gis:edit`), `remove` (`gis:delete`: delete, restore, deleteImpact), `post` (`gis:post`: post, discard) and `configure` (`gis:configure`: tiers, subnetworks, attachment rules); write procedures seed the organization's attachment rules on first use. The versioning engine (`versioning/`) is Majimap's as it is: every edit supersedes a version (compare-and-set on `is_head`), a branch's first edit is built from the client's base version of main, `merge.ts` is the pure field-level three-way merge, `post` applies a branch in a savepoint (all or nothing; integrity violations come back as `status: "invalid"`, conflicts as `"conflicts"`), deletes are tombstones, `restore` undoes one on main. A DMA's map data is keyed by its kernel area (`keyOf`/`normalize` make `id` the area id; the name is the area's, read with `areasById` from `kernel/areas.ts`, which also checks level "dma"). Every write checks the branch first (`versioning/branch-write.ts`): main needs `gis:post`; other branches go to `work.checkBranchWrite` (`wo-` is Work Orders' guard, `fld-<userId>` GIS's personal-branch guard, `field-` reserved and refused). Posting a job's branch needs the job completed or `override`, and a cancelled job's branch can only be discarded (from the `wo-` annotator's status). Logs (`logs.ts`) are always kept; the asset edit they imply happens only where the caller may write, otherwise the outcome is `stale`; Work Orders links a log only if it was recorded on the job's branch (`EvidenceRef.branch`). Wire format: locations are `{ lat, lng }` (the database's and `@flowless/network`'s), dates are `Date`; the resolvers convert to `GeoPoint` for the ports. GIS holds no customers: `service_connection.service_point_id` is optional, and a connection going live publishes `gis.connection_posted`. Outbox events (`events.ts`): `gis.condition_changed` (main only), `gis.connection_posted`, `gis.branch_submitted` / `.branch_ready_for_reconcile` / `.branch_cancelled` (the job effects); the consumer `gis.seed_attachment_rules` seeds `structure_attachment_rule` from `STRUCTURE_ATTACHMENT_RULES` on `entitlements.changed` (idempotent; `attachmentRules.set` never empties them, so "no rules" means "never seeded"). Post, discard, restore and configuration changes are audited (`gis.*`). Reports `gis.recent_findings` and `gis.condition_trend` are `defineReport`s; `summary` and `alerts` are procedures. `index.ts` exports `register(work)` (the 11 GIS kinds, all tier basic; asset and evidence resolvers; effects; the `fld-` guard; the reserved `field-`), the `gis_asset` file subject (read `gis:read`, add and remove `gis:edit`, manage `gis:post`; required photos are checked at post) and the reports. Tests: `modules/gis/test/test-support.ts` (`setupTestEnv`: four organizations, the roles, `photo`, `events`, `dmaArea`); `job-branches.test.ts` covers jobs end to end on the real GIS.
- Accounts (`modules/accounts`, Phase 3 F1): `accountsRouter` mounted at `accounts`: `customers.create/update/get/list/search/duplicates`, `contacts.add/update/remove`, `servicePoints.create/update/get/list`, and `create`/`get`/`list`/`search`/`nextNumberPreview` for accounts at the router's root. Procedures come from `accountsProcedures` (`procedures.ts`): `read` (`accounts:read`), `create` (`accounts:create`), `update` (`accounts:update`), each adding `ctx.viewer` (`userId` and `scope`). Scope (`access.ts`): a limited member sees service points whose scheme, zone, DMA or route is in scope, accounts through their service points and customers through their accounts; an account or customer with no service point or account yet is its creator's, so an enquiry can be finished; they may place a service point only inside their scope; everything else is NOT_FOUND. `numbering.ts` is pure (format schema, Luhn and mod 11 check digits, child letters `A..Z, AA`, `parseAccountNumber`); the `accounts.numbering` setting (`settings.ts`) is registered in `kernel/config-registry.ts`. `service.ts` is the only code touching the tables: numbers come from `issueAccountNumber` / `issueChildNumber` (locked counter row; sequences with no mod 11 digit or an already used number are skipped), contacts are normalised with `parsePhone` from shared-types (calling code from `kernel.regional`'s locale; placeholders are stored flagged and count as no phone, the first real contact of a channel becomes primary), and a service point's scheme, zone, DMA and route are checked with the kernel's `areasById` / `routesById` (`kernel/areas.ts`). Audit actions `accounts.customer_create/update`, `accounts.contact_add/update/remove`, `accounts.account_create`, `accounts.service_point_create/update`; events `accounts.customer_created`, `.account_opened`, `.service_point_created` (`events.ts`, JSON payloads, dates as ISO strings). Status changes are the lifecycle below (F3a); the category is an opaque uuid for Tariffs (F2). Tests: `modules/accounts/test/test-support.ts` (`setupAccountsEnv`: tenants A, B and an unlicensed C, roles, a scheme > zone > DMA chain, routes).
- Account lifecycle (`modules/accounts`, Phase 3 F3a: C-03, C-04, C-06, C-11): the `status` procedure (`accounts:change_status`: owner, admin, manager) carries `markPendingPayment`, `activate` (same as `activation.activate`), `makeDormant`, `reactivate`, `terminate`, `disconnectService`, `reconnectService`, `requestWriteOff`, `activation.tick/untick`; reads (`accounts:read`) are `commands.list`, `statusRules` and `activation.status`. `lifecycle-router.ts` holds the procedures, `commands.ts` the only code that changes a status (`runCommand(env, viewer, request)`: lock the account row, replay or CONFLICT on a repeated client id by fingerprint, plan with the pure `lifecycle.ts`, check gates or settlement, insert the `account_command`, update the account with `status_command_id`, audit `accounts.<kind>`, publish `accounts.account_status_changed`/`.service_status_changed`/`.account_activated`/`.account_terminated`); the database trigger refuses any other change of the status columns. `CommandEnv` (`procedureEnv(ctx)` or `systemEnv(tx, orgId)`) lets the system act with no user (source `system`). Pure files: `lifecycle.ts` (state machine), `gates.ts` (`activationConfigSchema`, `evaluateGates`), `status-rules.ts` (`chargesApplying`), `termination.ts` (`settleTermination`). Settings `accounts.status_rules` and `accounts.activation` are in `settings.ts` and the config registry. Ports in `sources.ts`, exported from the index: `registerGateSource(gateKey, source, { requires })` (asked only while every module in `requires` is licensed) and `registerTerminationCheck(check)`; tests reset them with null. `recheckActivation(tx, orgId, accountId)` is what other modules' consumers call in auto mode. `activate` needs the gates met; `override: true` needs `settings:manage`. `terminate` needs a settled position or `acknowledgeNoLedger`; the write-off approval kind `accounts.write_off` (`approvals.ts`, registered in `kernel/approval-registry.ts`, consumer `accounts.record_write_off_decision` in `kernel/consumers.ts`) is cited with `approvalId` and read with the kernel's `approvalOutcome`. `sweepStaleAccounts(db)` (`stale.ts`) runs in the worker with the finder `accounts.sweep_organizations`; it raises `STALE_ACTIVATION` and `ACCOUNT_NOT_ACTIVE_WITH_METER` (keys `account_stale:<id>`, `account_not_active_with_meter:<id>`, raised once, resolved by themselves; `openDedupeKeys` in `kernel/exception-store.ts`). Tests: `test/lifecycle.test.ts` (integration), `lifecycle.test.ts` and `rules.test.ts` (pure).
- Tariffs (`modules/tariffs`, Phase 3 F2): `tariffsRouter` mounted at `tariffs`: tariffs at its root (`list`, `get`, `create`, `update`, `addVersion`, `versions`, `inForce`, `nextEffectiveDate`), `simulateLateFee`, and `categories.*` (list, get, create, update, deactivate, reactivate, assignTariff), `chargeItems.*` (list, get, create, update, addAmountVersion, deactivate, reactivate), `invoiceTypes.*` (list, get, create, update, setLines, setLateFeeRule). Procedures come from `tariffsProcedures` (`procedures.ts`): `read` (`tariffs:read`) and `manage` (`tariffs:read` and `tariffs:manage`); every change is audited (`tariffs.*`) and publishes in the same transaction. Rates and amounts are bigint minor units (a rate is minor units per unit consumed, 82.50 is `8250n`; a flat amount is per billing month), so audit and event payloads carry them as decimal strings (`plain()` in `service.ts`). Pure files with no I/O: `content.ts` (zod content per tariff type, `validateTariffContent`, `bandsFor`, `chargeForUnits`, line-row mapping; bands are cumulative thresholds, `[0,6]` then `[6,20]`, first at 0, meeting exactly, last open, rates non-decreasing for increasing and non-increasing for decreasing), `dating.ts` (`versionInForce`, `versionSpans`, `nextPeriodStart`, `planEffectiveDate`; dates are `YYYY-MM-DD` strings in the organization's time zone, `todayIn(zone)`), `late-fee.ts` (`lateFee(rule, balance, daysOverdue, alreadyCharged)`, basis points, rounded once half up, a "month" is 30 days) and `invoice-policy.ts` (terms, overdue rule, `formatInvoiceNumber`). Versions, category assignments and charge amounts are insert-only: "version i is in force from its `effective_from` until the next one's"; a version that shares a still-future date replaces the earlier one (higher `version_no` wins), one dated today or earlier cannot be replaced (CONFLICT). `chooseEffectiveDate` (`service.ts`) is the single rule for T-03: the requested date, else the next period start from the `tariffs.policy` setting (`periodStartDay`, 1 to 28, default 1; today for the first version of something), refused when on or before `closedThrough(tx, orgId)`, the closed-period port (`closed-period.ts`; default null; Billing calls `registerClosedPeriodSource` from the module's `index.ts` in Phase 4). Invoice types: `applies_to` `application` or `account`; an application's type can never have overdue action `disconnect` (validation and a DB check); `allocateInvoiceNumber(tx, organizationId, invoiceTypeId)` (exported from `index.ts`, for Billing) takes the next number from `invoice_type_counter` with one upsert, so concurrent callers take turns. Defaults (`defaults.ts`, `ensureDefaults`): six categories, eleven charge items (no amounts) and five invoice types (the new-connection template carries application fee, connection fee, meter, materials, labour, deposit), added by code with `ON CONFLICT DO NOTHING` by the consumers `tariffs.seed_defaults_on_creation` (`organization.created`) and `tariffs.seed_defaults_on_licence` (`entitlements.changed` when Tariffs is newly licensed), both skipped while Tariffs is unlicensed, so the licence event is what seeds most organizations; write procedures do not seed. Published reads in `index.ts`: `categoryExists`, `categoriesById`, `categoryPricing`, `tariffVersionInForce`, `chargeItemByCode`, `allocateInvoiceNumber`. `accounts.account.category_id` stays an opaque uuid: Accounts does not import Tariffs (it must work without it), so nothing yet checks that a category exists when an account is opened; a caller that wants that uses `categoryExists`. Events (`events.ts`): `tariffs.tariff_version_created`, `.charge_item_created`, `.charge_item_amount_changed`, `.invoice_type_changed`. Tests: `modules/tariffs/test/test-support.ts` (`setupTariffsEnv`: tenants A and B with Accounts and Tariffs, C with Accounts only, roles).
- Applications, memberships, succession, relocation and change of name (`modules/accounts`, Phase 3 F3b: C-05, C-07 to C-10). Routers: `accounts.applications.*` (`application-router.ts`), `accounts.memberships.*`, `accounts.relocations.*`, `accounts.holders.*`, and at the root `succeed` and `changeName` (`changes-router.ts`). **Applications**: `applications.ts` is the only code changing one; the pure `application-stages.ts` is the stage machine (milestones `enquiry > survey > application > invoice > payment > installation > ready > converted`, a stage is a milestone reached, `rejected`/`cancelled` from any open stage, final stages final, only a stage waived by config is skipped) with the `accounts.application` setting (`survey`, `invoice` which covers invoice and payment, `installation`, each `required`; `relocation.surveyRequired`). Each step is a `application_event` row (client-mintable `id`, fingerprint like account commands: same id and request replays, anything else CONFLICT) and a trigger refuses a stage change without one. `create` takes an existing customer or `newCustomer` (created together, `createCustomer` in `customers.ts`), the opaque requested category (checked with Tariffs' `categoryExists` only while Tariffs is licensed), the place (checked and scope-asserted like a service point; an enquiry may have no place yet), and optionally a parent account with a `membershipClass`. `recordSurvey` (office, `accounts:update`; findings, `feasible`/`not_feasible`, materials note) asks for approval with `ctx.requestApproval(surveyApproval)` (K-05 kind `accounts.connection_survey`, `survey-approval.ts`, registered in `kernel/approval-registry.ts`; default policy ONE level `accounts:change_status`; a second level such as `billing:approve` or none at all is the organization's policy `approvals.accounts.connection_survey`, so 0, 1 or 2 approvals are configuration; a policy with no level approves at once). The application stays at `enquiry` with `survey_approval_state` pending until the consumer `accounts.apply_survey_decision` (`defineApprovalConsumer`, in `kernel/consumers.ts`) moves it to `survey` (idempotent: only a pending request that is the application's current one counts; a rejected one asks for a new survey). Not feasible: recorded, no approval, the office rejects. `submitApplication`, `markInvoiced(invoiceRef)`, `markPaid(paymentRef)`, `startInstallation`, `markReady` (`accounts:update`), `reject`, `cancel`, and `convert` (`accounts:create`): `markInvoiced`/`markPaid` take opaque references until Billing (Phase 4) and Payments (Phase 6) replace them with events consuming `accounts.application_stage_changed` and calling these use cases as the system. `convert` runs `openAccount` (`open-account.ts`, shared with `accounts.create` and succession: number, child letters, first holder row), `createServicePoint` (shared with `servicePoints.create`) and, when the invoice stage is used, the F3a `mark_pending_payment` command; activation stays F3a's gates. Pending survey approvals are not cancelled when an application ends (the consumer ignores them). **Work Orders** (`work-kinds.ts`, `register(work)` in the index, called from `wiring.ts`): kinds `connection_survey` (target location, review optional, GPS evidence, capture `feasibility`/`findings`/`materials`, completion event `accounts.connection_survey_completed`) and `relocation` (target account, capture `finalReading`/`initialReading`, event `accounts.relocation_work_completed`), both tier full, so offered only with Accounts and Work Orders licensed; an asset resolver (module `accounts`) answers for application and relocation ids, so the office raises the job in Work Orders with `workOrders.create({ kind, assetId: <application or relocation id> })` (Accounts does not create jobs itself: there is no published way for a module to raise one and none was added). Consumers `accounts.record_survey_from_job` (records the survey as the system and asks for approval as the technician; skipped when the application is no longer an enquiry or the job is already recorded) and `accounts.record_relocation_from_job` (readings and job id on an open relocation). The office path works with Work Orders and Inventory unlicensed (tested end to end). **Memberships** (`membership.ts`, `memberships.ts`): setting `accounts.membership` (classes with `key`, `label`, optional `connectionFeeChargeItemCode`, by code with no foreign key), `account.membership_class` validated against it and only on a child; `memberships.setClass` (`accounts:update`, audited, event `accounts.membership_class_changed`), `membershipFor(tx, accountId)` published for Billing. **Succession** (`succession.ts`, `succeed`, `accounts:change_status`): needs an ACTIVE or DORMANT account; opens a successor in the same state with its own number (no parent for `full_membership`, which needs a child; otherwise the parent is kept), the same or a new customer and category; the old account goes DORMANT through the F3a `make_dormant` command; service points move to the successor (or `servicePoints: "leave"`); `predecessor_account_id`/`successor_account_id` are set once; a `succeed` row in both command logs (the old one's payload has the result) and event `accounts.account_succeeded`. The balance transfer and reading handover are ports in `sources.ts` (`registerBalanceTransfer`, `registerReadingHandover`, optional `requires` modules, run inside the command's transaction keyed by the command id, a failure rolls everything back); with none the payload says `transfer: "pending_ledger"` and `readingHandover: "pending_metering"` for Phase 4 and 5 to reconcile. **Change of name** (`change-name.ts`, `changeName`): the holder changes from `effectiveDate` (today or earlier, after the current holder started) in the insert-only `account_holder` history (`holders.ts`: `holderAt(tx, accountId, date)`, `holdersOf`, published for Billing's split), `account.customer_id` follows only through a trigger-checked newest holder row; payload `closing_reading_pending: true` unless the reading port or the office (`closingReadingRef`) supplied the closing reading; event `accounts.holder_changed`. **Relocation** (`relocations.ts`, `relocations.*`, `accounts:change_status`): `request` > `recordSurvey` (required by default) > `recordWork` (final and initial readings as text) > `complete` (creates the new service point from the new place with its zone/DMA/route, decommissions the old, `relocate` command row, event `accounts.service_point_relocated`; the tariff is re-derived by whoever reacts to that event; account number and status unchanged) or `cancel`; fee item codes are recorded, not invoiced. Non-status commands (`succeed`, `change_name`, `relocate`) use `account-changes.ts` (`logChange`, `earlierChange`). Tests: `test/applications.test.ts`, `test/changes.test.ts`, pure `application-stages.test.ts`.
- Data quality (`modules/accounts`, Phase 3 F4: C-12): `accounts.dataQuality.rules` (catalogue with the effective configuration and `state`: `enabled`, `disabled` or `no_source`), `.summary` (examined = accounts not terminated within the member's scope, flagged, clean, `cleanPercent`, a count per rule, `categoriesChecked`), `.findings({ rule, after?, limit })` (accounts in number order with customer, area and route labels and `why`; PRECONDITION_FAILED for a disabled rule or one with no source) and `.customerDuplicates({ after?, limit })` (groups by shared normalised phone, national id or registration number); all `accounts:read`, scope applies like the account lists (a limited member's duplicate groups only hold customers they can see). The catalogue (`DATA_QUALITY_RULES`) is in shared-types; the per-organization choices are the `accounts.data_quality` setting (`data-quality-config.ts`: per rule `enabled`, `severity` info|warning|critical, `raiseExceptions`, all optional, unknown keys ignored). Each rule is an indexed predicate on `accounts.account` in `data-quality-queries.ts`; the summary is one `count(*) filter` per rule in a single pass, the findings page is keyset on the account number. Both are reports (`accounts.data_quality_summary`, `accounts.data_quality_findings`, registered in `kernel/report-registry.ts`, X-04 guard and canary apply); a report cannot know the viewer, so the scope arrives as a parameter (`scopeOf(viewer)`) and becomes the same `accountVisible` filter. What SQL cannot know is gathered once per request by `data-quality-facts.ts`, only for the rules switched on: `zone_equals_route` reads the distinct (scheme, zone, DMA, route) placements of live service points and judges each with the kernel's published `routesById`/`areasById` (pure `data-quality-placement.ts`; interpretation: the route has the same name as the point's zone, scheme or DMA, or the route's `area_id` is neither the point's most specific area nor above nor below it); `account_category_missing` checks `category_id is null` and, only with Tariffs licensed, ids that Tariffs' `categoriesById` says are unknown or deactivated. `active_metered_no_meter` and any other rule another module decides use the port `registerDataQualitySource(ruleKey, source, { requires })` (source returns the account ids that break the rule; without a registered, licensed source the rule is `no_source` and skipped, never failed; tests reset it with null). Terminated accounts are never examined; each rule has its own `appliesTo` statuses. `sweepDataQuality(db, { limit = 100, batch = 50 })` (`data-quality-sweep.ts`, worker, hourly, finder `accounts.data_quality_organizations`) raises one `DATA_QUALITY` exception per account and rule for rules with `raiseExceptions` (key `dq:<rule>:<accountId>`, owner = who opened the account, area and route of the first (for `zone_equals_route`, first offending) service point, severity in the detail), only for findings not already open and at most `limit` per organization per run in account-number order; open ones resolve by themselves when the finding clears, the account ends or the rule stops raising; a rule with no source is left alone. Tests: `test/data-quality.test.ts` (integration), `data-quality.test.ts` (pure) and shared-types `data-quality.test.ts`.
- Mount a module router in `root.ts` at the camelCase of its module key (`workOrders` for `work-orders`); `src/module-matrix.test.ts` relies on it and lists the kernel routers. `test-support.ts` has `procedures()` and `callPath()` for tests that walk every endpoint. Adding a procedure means adding its calls to `CALLS` in `src/isolation-canary.test.ts` (aim id inputs at tenant B's records); a new tenant table must be seeded for B in that test's `seedB`, and a new module schema added to its `TENANT_SCHEMAS`.
- Layout: `src/trpc.ts` (context and base procedures), `src/root.ts` (`appRouter`, `export type AppRouter`), `src/kernel/*`, `src/modules/<module>/{router,service,events,index}.ts`.
- Module routers build procedures only from `moduleProcedure(module)`. That runs `withTenant` (RLS) and the entitlement check. Never use the raw DB client.
- A module touches only its own `@flowless/db` schema. It reaches other modules through their `index.ts` or through events.
- Long-running work is enqueued for `apps/worker`; procedures never run billing, imports or reconciliation inline.
- Server-only package (Node). `apps/web` imports it at runtime. `apps/mobile` may only `import type { AppRouter }`.
- No build step: consumers import `src/index.ts` directly via `exports`. Scripts: `pnpm lint`, `pnpm check-types` (or `pnpm turbo run check-types --filter=@flowless/api`).
