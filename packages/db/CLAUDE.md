# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## `@flowless/db`

Drizzle (postgres-js) client, schema, migrations and tenant isolation. Shared package conventions are in the root `CLAUDE.md`; boundary rules are in `docs/build-plan.md` → "Code layout".

- `src/schema/<module>.ts`: one file per module, each in its own Postgres schema (`pgSchema("kernel")`). Re-export it from `src/schema/index.ts`.
- `src/schema/auth.ts` is generated by Better Auth (see `packages/auth/CLAUDE.md`); never edit it by hand. It is not re-exported from the index; only `packages/auth` imports it, via `@flowless/db/auth-schema`. The tenant table is `auth.organization`; module tables reference its `id`.
- Every tenant table ends with `(t) => [tenantPolicy(t.organizationId)]` (from `src/tenant.ts`). That generates `ENABLE ROW LEVEL SECURITY` plus the policy for role `flowless_app`. The policy fails closed: with no tenant set, no rows match.
- Runtime code reads and writes tenant data only through `withTenant(db, organizationId, tx => ...)`. It sets `app.organization_id` for that transaction only.
- Roles: group roles `flowless_app` (module schemas, subject to RLS) and `flowless_auth` (`auth` schema only), both NOLOGIN and NOBYPASSRLS, owning nothing. The login roles from `DATABASE_URL` and `DATABASE_AUTH_URL` each belong to one of them. `migrateDatabase` (`src/migrate.ts`) creates them before migrations run.
- Privileges are granted per schema in migrations (`migrations/0001_schema_access.sql`), never globally, so neither role can reach the other side. Append-only tables must `REVOKE UPDATE, DELETE` in their migration.
- Migrations live in `migrations/`. Workflow:
  1. Edit the schema.
  2. Run `pnpm db:generate`, then review the SQL.
  3. A new module schema also needs a custom migration (`npx drizzle-kit generate --custom --name <module>_access`) that copies the kernel block from `0001_schema_access.sql`.
  4. Run `pnpm db:migrate`.
- `@flowless/db/testing` (Node only; never import it from app code): a package's Vitest config adds `@flowless/db/vitest-setup` as `globalSetup`, which starts one Postgres with PostGIS (Testcontainers, `postgis/postgis:17-3.5-alpine`, the docker-compose image) per run, migrates a template database and seeds the canary `tenants.a` and `tenants.b` (in `auth.organization` plus their `kernel.organization_settings`). In each test file, `startTestDatabase()` clones that template into a private database, so files never share state; `stop()` drops it. Use `app` (subject to RLS) in tests. `auth` is the Better Auth role. `admin` bypasses RLS and is only for seeding and checking raw state. Drizzle wraps Postgres errors, so assert on `cause.message`.
- Kernel hierarchy (K-02): `area` (level enum `area_level`) and `route`, each with a self-referencing composite foreign key on `(organization_id, parent_id)` so trees never cross tenants; `member_area_scope` and `member_route_scope` hold scope restrictions (K-03).
- `kernel.audit_log` (K-06, NF-07): write only with `recordAudit` (`src/audit.ts`) inside the transaction of the change. Append-only (no UPDATE, DELETE or TRUNCATE for the app role); the auth role may only insert. The `kernel.audit_chain` trigger stamps `occurred_at`, `chain_index` and SHA-256 hashes; never set them. `kernel.verify_audit_chain()` checks the current tenant. If you add a column, include it in `kernel.audit_digest` in a new migration.
- `kernel.outbox_event` and `kernel.consumer_receipt` (K-09): write events with `enqueueEvent` (`src/outbox.ts`) or the api's `ctx.publish`; `kernel.claim_outbox(batch, lease_seconds)` is the worker's only cross-tenant read. The auth role may insert events.
- `kernel.exception` (X-02, NF-24) and `kernel.job` (NF-12): the exception owner's foreign key to the membership sets only `owner_user_id` to null when they leave (`0013_kernel_exception_owner.sql`); `kernel.claim_jobs(batch, lease_seconds)` is the worker's cross-tenant read for jobs.
- `kernel.config_version` (K-10): one row per version of a setting, append-only (no UPDATE, DELETE or TRUNCATE for the app role). The value in force is the newest `effective_from` that has passed. `kernel.organization_settings` holds only the currency; time zone and language are the `kernel.regional` setting (moved by `0014_kernel_config_store.sql`).
- `kernel.approval_request` and `kernel.approval_decision` (K-05): one pending request per kind and subject (partial unique index); decisions are append-only; `kernel.overdue_approvals(batch)` is the worker's cross-tenant read for SLA escalation.
- `kernel.file` (K-08): file metadata; the id comes from the device; `storage_key` starts with the organization id; bytes live in object storage, never in Postgres.
- `kernel.notification` (K-07): in-app inbox; composite foreign key to the membership with `on delete cascade`.
- `kernel.support_grant` (K-12): no DELETE or TRUNCATE for the app role; the window is at most 72 hours by a check constraint. Audit source `support` is in `AUDIT_SOURCES`.
- `kernel.organization_module`: licensed modules (K-04), module keys as text validated against `MODULE_KEYS` in shared-types.
- A kernel table may reference a membership with a composite foreign key to `auth.member(organization_id, user_id)` (unique constraint from `migrations/0004_auth_member_organization_user.sql`) and `on delete cascade`, as `kernel.member_permission` does; referential actions bypass RLS and run as the table owner, so neither runtime role needs access to the other schema.
- PostGIS is enabled by `migrations/0019_postgis.sql` (types and functions in `public`).
- Geometry (`src/geometry.ts`, ported from Majimap): `pointColumn`, `lineStringColumn`, `polygonColumn` are SRID 4326 custom types whose values are `LatLng` (`{ lat, lng }`) or arrays of them; reads decode PostGIS's hex EWKB (either byte order), polygons are one closed ring (closed on write, holes refused), Z/M refused. Every geometry column gets a GiST index (`index(...).using("gist", col)`); `gis-work-orders.test.ts` checks it.
- Module schemas `gis` (`src/schema/gis.ts`) and `work_orders` (`src/schema/work-orders.ts`), Phase 2, each also exported as `@flowless/db/schema/<module>` so the module imports only its own; grants in `0021_gis_access.sql` and `0022_work_orders_access.sql`. Conventions: foreign keys between tables of a module (and to `kernel.area`/`route`) are composite with `organization_id`; user columns that are history have no foreign key, a member who must exist uses the composite membership key (nullable ones `ON DELETE SET NULL (col)` in a custom migration, as `work_order_assignee_fk`); references into another module are ids with no foreign key.
- `gis`: `asset` is the stable identity of every versioned asset (GIS's own, no shared assets table). `node`, `pipe`, `structure`, `service_connection` are branch-versioned: a row is a version (`version_id`), `id` is the asset, one `is_head` per (organization, id, branch), `is_deleted` rows are tombstones, `main` is live. `dma` is map data on the kernel's DMA (`area_id`, versioned the same way, one head per area and branch) with `dma_boundary_valve` per DMA version. `tier`, `subnetwork` and `structure_attachment_rule` (per organization, seeded from `STRUCTURE_ATTACHMENT_RULES`) are configuration. `condition_log`, `valve_state_log` are append-only. The `gis.check_structure_attachment` trigger (`0023_gis_structure_attachment.sql`) refuses a live node head housed in a structure that is not live on its branch or main, or whose type the organization's rules do not allow. `service_connection.service_point_id` is the Accounts service point, by id only.
- `work_orders`: `work_order` (primary asset as `(asset_module, asset_id)`, no foreign key; `area_id`/`route_id` to the kernel; assignee SET NULL on leaving), `work_order_asset`, `crew`, `crew_member` (cascade with the membership), `work_order_counter`; append-only history: `work_order_event` (client-minted ids, GPS), `work_order_change_set`, `work_order_log_link`, `work_order_comment`, `work_order_capture` (newest row per job is the one in force). `work_order.overdue_at` marks a job whose SLA breach was raised (`0024`); `work_orders.overdue_work_orders(batch)` (`0025_work_orders_overdue.sql`, SECURITY DEFINER, granted to `flowless_app` only) is the worker's cross-tenant read for breaches, limited to organizations licensed for `work-orders`. Status, priority and similar lists are text with check constraints from shared-types (`work.ts`); GIS enums are Postgres enums from shared-types (`gis.ts`).
- `accounts` (`src/schema/accounts.ts`, Phase 3 F1, also `@flowless/db/schema/accounts`; grants in `0027_accounts_access.sql`): `customer` (person or organization; national id and registration number held normalised, deliberately not unique), `customer_contact` (`value` as typed, `normalized` 254-format digits or lower-case email, `is_placeholder` for numbers such as 25400000000, at most one primary per customer and channel), `account` (number unique per organization, composite `parent_account_id` self key, `suffix_index` unique per parent, opaque `category_id` with no foreign key, both status axes as text with checks, a disconnected service always has a reason), `account_counter` (one row per organization and scope, `main` or `child:<parent id>`, taken with one `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` so the row lock serialises allocation) and `service_point` (composite keys to `kernel.area` for scheme, zone and DMA and to `kernel.route`, a PostGIS `location` with a GiST index, `gis_connection_id` by id only). The app role cannot DELETE or TRUNCATE customers, accounts, service points or the counter, and cannot TRUNCATE contacts (a contact can be removed).
- `accounts` lifecycle (Phase 3 F3a, `0030_accounts_lifecycle.sql`, `0031_accounts_lifecycle_access.sql`): `account_command` (append-only status command log: client-mintable id, kind, from and to on both axes, `service_reason`, required `reason`, actor or `source = 'system'`, `payload`, request `fingerprint`) and `activation_check` (insert-only checklist, newest `seq` per account and gate wins; an untick is a row); the app role cannot UPDATE, DELETE or TRUNCATE either. `account.status_command_id` and the trigger `accounts.guard_account_status` make the status columns change only together with a new command of that account whose from-state is the old row and to-state the new row (the stronger option over a session flag: no code path, including the admin role, can skip the log; a forged row would still be a visible log entry). The check `account_service_needs_live_status` keeps NEW, PENDING_PAYMENT and TERMINATED accounts DISCONNECTED. `accounts.sweep_organizations(after_id, batch)` is the stale-account sweep's cross-tenant finder (SECURITY DEFINER, granted to `flowless_app` only): organization ids licensed for `accounts` with an account in NEW or PENDING_PAYMENT or an open exception the sweep raised.
- `accounts` applications, holders, relocations (Phase 3 F3b, `0032_accounts_applications.sql`, `0033_accounts_applications_access.sql`): `application` (customer, opaque `requested_category_id`, optional parent account and `membership_class`, requested place with composite keys to `kernel.area`/`route`, `stage`, the survey's findings and K-05 request id and state, opaque `invoice_ref`/`payment_ref`, `account_id`/`service_point_id` once converted; a check ties `stage = 'converted'` to `account_id`), `application_event` and `relocation_event` (append-only, client-mintable ids, fingerprint, actor or `source = 'system'`), `relocation` (the service point being closed, the new place, `status`, fee item codes as jsonb, readings as text, job id by id only; one open relocation per service point by a partial unique index) and `account_holder` (insert-only holder history: `valid_from` date, unique per account, `previous_closing_reading_ref`; filled for every existing account by the migration). `account` gained `membership_class` (only with a parent), `predecessor_account_id` and `successor_account_id` (composite self keys, each unique where set, so one successor per account). Triggers: `guard_account_links` (`customer_id` changes only to the customer of the newest `account_holder` row; the succession pointers are set once), `guard_application_stage` and `guard_relocation_status` (a stage or status changes only when an event describing that move exists; moves are one-way so an event is used once). The app role cannot UPDATE, DELETE or TRUNCATE the three history tables nor DELETE or TRUNCATE `application` and `relocation`. `account_command.kind` also accepts `succeed`, `change_name` and `relocate` (rows with from-state = to-state).
- `accounts` data quality (Phase 3 F4, `0034_accounts_data_quality.sql`, no table): `accounts.data_quality_organizations(after_id, batch)` is the data-quality sweep's cross-tenant finder (SECURITY DEFINER, granted to `flowless_app` only): organization ids licensed for `accounts` that have ever set `accounts.data_quality` or still hold an open `DATA_QUALITY` exception. The rule queries use only existing indexes.
- `tariffs` (`src/schema/tariffs.ts`, Phase 3 F2, also `@flowless/db/schema/tariffs`; `0028_tariffs.sql`, grants in `0029_tariffs_access.sql`): `category` and `category_assignment` (a category's tariff, standing charge, meter rent and discount from a date), `tariff` (type and `flat_basis` fixed), `tariff_version` (`effective_from` date, `version_no`, no end column: a version lasts until the next one starts) with `tariff_version_line` (bands, a uniform rate or flat amounts as rows; `rate` bigint minor units), `charge_item` and `charge_item_amount`, `invoice_type` (numbering, terms and overdue columns, with check constraints for the terms shape and for T-09: an `application` type cannot have `disconnect`), `invoice_type_counter` (taken with one `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`), `invoice_type_line` and `late_fee_rule`. All eleven have RLS and composite tenant keys. The app role cannot UPDATE, DELETE or TRUNCATE `tariff_version`, `tariff_version_line`, `charge_item_amount` or `category_assignment`; cannot DELETE or TRUNCATE the identities (`category`, `tariff`, `charge_item`, `invoice_type`) or the counter; `invoice_type_line` and `late_fee_rule` are configuration that can be deleted and replaced. Check constraints that combine columns wrap the whole expression in `coalesce(..., false)`, because a comparison with NULL passes a check. `created_by_user_id` is null on rows the seed consumer wrote.
- `billing` (`src/schema/billing.ts`, Phase 4 P4-2, also `@flowless/db/schema/billing`; `0035_billing.sql`, grants and triggers in `0036_billing_access.sql`): the append-only sub-ledger and documents. `document` (kind invoice, credit_note, debit_note or reversal; opaque `invoice_type_id`, `number`, `number_sequence` from Tariffs' `allocateInvoiceNumber`; opaque account; bigint `total` signed by effect on the balance, `line_count`; `related_`, `reverses_` and `replaces_document_id` self keys, reverses and replaces unique; `idempotency_key`), `document_line` (signed `amount`, `service_from`/`service_to`, opaque `tariff_version_id` required for consumption and true_up lines and `charge_item_amount_id` for standing, charge, fee, penalty and deposit lines (T-04), `calculation` jsonb), `ledger_transaction` (entry type, currency, sealed by `entry_count`, optional document, `reverses_transaction_id` unique, `idempotency_key`) and `ledger_entry` (debit or credit, positive amount, ledger account, dimensions account, service point, scheme, zone, category, charge item and type, invoice type, payment channel, service period, tariff and charge amount versions, optional document line key; currency tied to the header by composite key). All four have RLS and composite tenant keys, and the app role has no UPDATE, DELETE or TRUNCATE on them. Deferred constraint triggers (`check_transaction_balanced`, `check_document_total`) refuse at commit a transaction whose entries are not exactly `entry_count` or whose debits differ from credits, and a document whose lines are not `line_count` or do not sum to `total`; they fire on the driver at commit, so the error is not wrapped in `cause`. Balances are never stored; the module derives them. All cross-module references are opaque ids.
- Scripts: `lint`, `check-types`, `test`, `db:generate`, `db:migrate`.
- Server-only (Node). `apps/mobile` must never depend on it.
